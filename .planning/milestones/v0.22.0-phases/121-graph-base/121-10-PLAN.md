实现 `@pytest.mark.perf def test_largest_repo_memory_calibration(...)`：
① **数据源二选一，用例自适应**：优先探测真实库中 `Symbol` 行数最多的仓库（`Symbol.objects.values("repository_id").annotate(n=Count("id")).order_by("-n").first()`）；开发/CI 库为空时回落到**合成图**（按 100k 节点 / 300k 边、5 节点属性 / 3 边属性、UUID 字符串键的形态用 `nx.MultiDiGraph` 直接造）。两种路径都要在输出里注明用的是哪种。
② **双计量**：`tracemalloc.start()` → 装配 → `tracemalloc.get_traced_memory()` 峰值增量；同时用 `resource.getrusage(resource.RUSAGE_SELF).ru_maxrss` 取 RSS 增量（注意 macOS 单位是字节、Linux 是 KB，用例内按 `sys.platform` 换算并注明）。
③ 与 `estimate_graph_bytes(node_count, edge_count)` 比对，算出三组比值：`tracemalloc / estimate`、`rss / estimate`、`rss / tracemalloc`。
④ 同时记录本仓真实的 **边:节点比**（假设 A2 的校验；RESEARCH 基准假设 3:1）与建图耗时（`add_nodes` / `add_edges` 分段）。
⑤ 断言部分保持**宽松但非空**：断言 `estimate_graph_bytes` 的估值不低于 `tracemalloc` 实测的 90%（估算不能显著低估，否则准入判据形同虚设）。若断言失败，说明常数需上调——这正是本用例的价值。
⑥ 用 `print` / `logger.info` 输出一张 markdown 表（nodes / edges / edge:node ratio / tracemalloc MB / RSS MB / estimate MB / 三组比值 / 建图耗时），便于直接粘进 SUMMARY。
