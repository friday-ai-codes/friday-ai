```
def reconcile_cross_repo_apis(blueprint: Any) -> dict
```
docstring 写清入参形状（**完整蓝图 content dict**，读 `repo_associations` 与 `api_contracts`）。字段名**已按 111 冻结 schema 实测确认，直接按此写**（`server/services/process_runtime/blueprint_schema.py:504-582`，实现时可再 `rg -n "api_contracts" -A 80` 复核）：
- `api_contracts[]` required = `["id", "name", "kind", "direction"]`；`direction` ∈ `provided|consumed`；`repository_id` 是归属仓；`method` / `path` / `request_schema` / `response_schema` 平级可选。
- ⚠️ **无顶层 `availability`**。可用性在 `data_source` 下：`data_source = {from_service, from_api, fields_needed: string[], availability: enum("existing","needs_support"), support_repository_id, notes}`（`:544-569`）。本模块的读与写**一律走 `data_source.*` 路径**，`.get("data_source") or {}` 逐层防御。

**恒定三键返回**：
```
{
  "gaps": [{"repository_id", "api", "reason": "no_provider"}],
  "conflicts": [{"api", "provider_repository_id", "consumer_repository_id",
                 "field": "method|path|request_schema|response_schema|direction",
                 "provider_value", "consumer_value"}],
  "missing_support_repos": [{"repository_id", "api", "support_repository_id"}],
}
```
（形状恒定，下游无需判空分支——对齐 `blueprint_route` 的约定。）

判定逻辑：
1. 建 provider 索引：所有 `provided` 项按 `(repository_id, name, method, path)` 收集。
2. 逐条 `consumed`：
   - 找到 provider → 逐字段比对（`method` / `path` / `request_schema` / `response_schema`）。任一不一致 → 进 `conflicts`（**带 provider/consumer 双值，便于澄清问题直接引用**），**绝不静默拍板取其一**。
   - 找不到 provider → 进 `gaps`（`reason="no_provider"`）；此时调用方应把该条 **`data_source.availability`** 置 `needs_support`（B4）。
   - 若该条已标 **`item.get("data_source", {}).get("availability") == "needs_support"`**：校验 **`data_source.support_repository_id`** **非空且出现在 `repo_associations[].repository_id` 集合中**；不满足 → 进 `missing_support_repos`（语义 = 缺协作仓，调用方抛澄清）。⚠️ **绝不读顶层 `availability`**；`data_source` 缺失视为「未标注可用性」，不触发本检查（但若同时无 provider 仍会进 `gaps`）。
3. 逐层 `isinstance` + `or []` 防御；非 dict 直接 `continue`；整个函数**不抛**。

新建 `server/tests/services/process_runtime/test_blueprint_reconcile.py`（**零 DB 纯函数测试**，模块 docstring 编号列守护点）：
- ⭐ **consumed 无 provider**：A 消费 `GET /x`，无人提供 → `gaps` 含该项且 `reason == "no_provider"`。
- ⭐ **needs_support 缺 support_repository_id**：`data_source.availability == "needs_support"` 但 `data_source.support_repository_id` 为空 → `missing_support_repos` 非空。
- ⭐ **support_repository_id 不在 repo_associations**：`data_source.support_repository_id` 填了但该仓不在关联清单 → 同样进 `missing_support_repos`（**缺协作仓的两种形态都被捕获**）。
- ⭐ **顶层 availability 不被识别（B4 防回归）**：一条 consumed 只写**顶层** `availability="needs_support"`（无 `data_source`）→ **不进** `missing_support_repos`（证明判定只认 `data_source.*`）；另一条把同样语义写进 `data_source` → 正常进 `missing_support_repos`。两条并列断言，杜绝路径写错还「看起来通过」。
- ⭐ **字段不一致**：provider `POST /x`、consumer `GET /x` → `conflicts` 非空且 `field == "method"`，`provider_value`/`consumer_value` 各就位。
- `request_schema` / `response_schema` 不一致各一例。
- **完全闭环**：provider 与 consumer 逐字段一致 → 三键全空（`{"gaps": [], "conflicts": [], "missing_support_repos": []}`）。
- **绝不抛**：传 `None` / `{}` / `{"api_contracts": "not-a-list"}` / 项内字段类型错乱 → 均返回三键空 dict。
