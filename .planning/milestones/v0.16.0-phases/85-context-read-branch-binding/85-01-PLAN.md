<objective>
把项目上下文（DOC-01~05 五文件正文 + active 项目记忆 + 工件）物化进 `delivery_knowledge` 向量库与交付知识图谱，实现 CTX-01 的「可 RAG」写半与 CTX-02 的「沉淀进图谱可索引 + 关联扩充」。新增 `project_doc` / `project_memory` 两个 normalizer（镜像既有 `sources/artifact.py`），在记忆 / 文件 / 飞书同步三处写收口挂写时增量材料化钩子（fail-soft、带 `initiated_by_user_id`），并提供兜底全量重建 management command + apscheduler 定时 job。

Purpose: 让项目全部上下文可被任意来源召回的「数据地基」就位——读侧（Plan 02）与分支反查召回（Plan 04）都依赖本 plan 把内容写进 `delivery_knowledge`。
Output: 2 个 normalizer + 注册、`aschedule_ingestion` 归因透传、3 处写时钩子、兜底重建命令 + 定时 job、Wave 0 测试。

## A1 架构口径决策（collection 布局，MUST 显式记录，用户可否决）

**决策：以既有 `delivery_knowledge` Qdrant collection 作为「项目上下文专属、逻辑独立于代码 RAG」的承载，通过新增 `source_kind`（`project_doc` / `project_memory`，`artifact` 已存在）+ 复用 `EntityKind.DOCUMENT` 做逻辑隔离，不新建第二个物理 collection。**

- 满足锁定决策「独立于代码 RAG collection」：代码 RAG 是 per-repo 的 `code_index_{repository_id}`（`QdrantService.get_collection_name`）；`delivery_knowledge` 本就与之物理分离，且 `access_scope` 已按项目 visibility 隔离召回范围。
- 满足 CTX-02「复用 `KnowledgeEntity`/`KnowledgeEdge`」：图谱实体/边即写入 `delivery_knowledge` 向量空间。
- **被否决的备选**：另起第三个物理 collection `project_context`。否决理由——会与 CTX-02 形成双重向量化（同一份内容既进 `delivery_knowledge` 又进新 collection），并要求重写一整套 collection 生命周期 / 召回 / scope / 重建，收益仅「物理隔离」而 visibility 隔离 `delivery_knowledge` 已具备。
- 若用户坚持独立物理 collection，需在执行前 veto 本决策；届时本 plan 须扩 collection 生命周期套件（不在当前范围）。

## 持久化口径解读（"durable + fail-soft" 锁定意图，WARNING 5）

锁定决策措辞「写时增量经 **durable 任务**，带 `initiated_by_user_id`；失败 fail-soft 不阻断业务」。本 phase 的交付口径是 **写时进程内增量（`aschedule_ingestion` → `transaction.on_commit` → `run_in_background`，带 `initiated_by_user_id`）+ 兜底定时全量重建（apscheduler job → `rebuild_project_context`）+ content_hash 幂等短路** 三者合成的跨重启安全网，而非引入新的 Procrastinate durable 队列行。理由：

- **沿用既有摄取现状不造两套**：`aschedule_ingestion` 全仓现状即 `on_commit`→`run_in_background`（5 个既有 source 同款），项目上下文量级低，复用零回归（RESEARCH Alternatives）。
- **跨重启安全网由"定时全量重建 + content_hash 幂等"承担**：若进程在写时增量投递后、摄取完成前重启而丢任务，兜底定时全量重建会按 source 重新 `aschedule_ingestion`；content_hash 短路保证对未变内容是幂等空操作、仅补齐真正缺失/漂移的向量。即"最终一致"由定时兜底闭合，不依赖单条任务的跨重启持久化。
- **fail-soft 不反噬**：写时钩子 best-effort（`except: pass`），`aschedule_ingestion` 内部亦吞异常 + warning，材料化失败绝不阻断记忆/文件/同步业务写。
- 若未来需"单条写时任务跨重启不丢"的强持久化，再升级为 Procrastinate durable（接口已存在，届时仅换调度后端，normalizer/钩子不变）——本 phase 不需要，故不引入。
</objective>
