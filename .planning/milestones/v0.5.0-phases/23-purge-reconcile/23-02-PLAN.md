<objective>
构建『对账 + 两模式清理』的服务与 API 地基：`compute_reconciliation(repository_id)` 对比"已索引文件集合 vs 现行排除规则"（复用 Phase 22 `build_matcher_for_repo`，EXCL-06），列出差异；匹配器构造失败时标 `degraded`/`error` 而非谎报"已一致"（W3）。`run_cleanup(repository_id, mode)` 对差异文件逐一调 Phase 23-01 的 `purge_file` 删净派生索引面（EXCL-04），清理后调度 repo_summaries/repo_index_nodes 重建，并埋清理审计事件（D-04）。

清理在后台异步执行（D-04），其结果（尤其敏感清理"哪些操作记录面已清 / 未清(unscrubbed) + caveat"）必须能回到客户端——故每次清理持久化一条 `CleanupRun`，并暴露状态查询端点（W1/W2，进度/结果可查询，不靠静态文案）。REST API：`GET …/reconcile/` 返回差异（含 degraded）、`POST …/reconcile/` 接受 `{mode}` 派发后台清理并返回 `run_id`、`GET …/reconcile/status/` 返回最近一次 `CleanupRun`。`mode=sensitive` 分支委托 23-03 的 `services.sensitive_purge.purge_sensitive_planes`（懒导入，普通模式无依赖），其返回 dict（含 unscrubbed/caveat）落入 `CleanupRun.sensitive`。

Purpose: 这是 EXCL-06 对账与 EXCL-04 普通清理的服务/接口主干——把 23-01 的单文件删除入口升级为"规则驱动的批量对账清理"，让对账失败可见（degraded）、让后台清理结果（含敏感未清面）诚实回流前端（CleanupRun 状态查询），并为 23-03 敏感面与 23-04 前端 UI 立好契约。
Output: `server/services/purge_reconcile.py`（新增）、`CleanupRun` 模型 + 迁移、`RepositoryReconcileView` + `RepositoryCleanupStatusView` + 路由 + serializer、对账/普通清理 + 状态查询守护测试。
</objective>
