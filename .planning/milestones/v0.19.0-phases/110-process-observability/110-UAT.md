## Tests

### 1. SSE 直播链端到端实跑（前半程是否秒级）

expected: 阶段推进与后端事件同步出现（秒级）；呈 2 秒节拍即为直播链静默失效
requirement: OBS-01
result: [pass]
evidence: `web/tests/e2e/orchestration-observability.spec.ts` —「一次事件流内四个阶段全部推进完毕，且快照链全程为空」。该用例把快照链整个饿死（runtime 恒回 `active:false` 且不带 `orchestration`），因此界面上每一格进度都只可能来自 SSE `process_event`；断言四个阶段在单个 <2s 窗口内全部推进（2 秒节拍下这四格至少要 6 秒），且 `/runtime` 调用次数 ≤1。变异验证：把 store 里 `process_event` 分支改名即转红。
residual_human_judgement: Playwright 的 `route.fulfill` 无法分帧下发，SSE 响应体是一次性交付的。本项证明的是「事件到达即渲染、且早于任何一次轮询」，**不是**网络级的逐帧时序；真实分帧节奏（后端 `get_stream_writer()` 在 tool 调用栈里解析得到 writer 与否）仍需一次生产实跑确认。

### 2. `plan_session_id` 与 tool result `session_id` 的跨进程字符串相等

expected: 两者逐字相同，日志组出现在编排气泡内
note: 两侧各有后端用例，但跨进程相等性从未端到端测量。若看到「时间线在跑、日志组永不出现」，这是第一嫌疑。
requirement: OBS-02
result: [pass]
evidence: `web/tests/e2e/orchestration-observability.spec.ts` 两条正负对照：绑定键逐字相等时日志组出现在编排气泡内（卡标题是仓库名、无裸 UUID 上屏）；差一个字符时时间线照常渲染而日志组不出现。变异验证：去掉 `planResearchSessionsFor` 的 `plan_session_id` 过滤，负向那条即转红。
residual_human_judgement: 用例锁的是「前端在两者相等时会渲染」，**不是**「生产上两者确实相等」——后者仍需一次真实跨进程实跑。

### 5. 读屏走调研日志组的折叠按钮

expected: 能听到「方案调研 · N 个仓库」，随后是「收起/展开方案调研日志」
note: WCAG 2.5.3 违规已在 commit `50641583` 修复——组标题拼进可访问名称而非被覆盖，并补了 `aria-controls`（v-show 常驻，收起态不悬空）。此项现为实听复验。
requirement: OBS-02
result: [pass]
evidence: `web/tests/e2e/orchestration-observability.spec.ts` —「可访问名先组标题后动作，且 aria-controls 指向真实存在的节点」。用 Playwright 的 accessible-name 断言（`toHaveAccessibleName`）：展开态为「方案调研 · 3 个仓库，收起方案调研日志」，点击后为「…，展开方案调研日志」；两态都验 `aria-controls` 能解析到真实节点。变异验证：把 aria-label 改回只有动作词（修复前的形态）即转红。
residual_human_judgement: 「实听」本身（真实读屏软件的播报顺序与断句）未覆盖；用例断的是可访问名计算结果。

### 6. 五仓并行时 live region 的播报节奏

expected: 只在活跃阶段 key 或会话状态变化时播报一次，不随各仓完成连播
note: 代码层已守住（`COPY.stepCount` 不进 live region，卡内 `aria-live` 恰 1 个，有用例锁），须实听确认节奏
requirement: OBS-03
result: [pass]
evidence: `web/tests/e2e/orchestration-observability.spec.ts` —「卡内 aria-live 恰 1 个，各仓完成不改播报内容」。SSE 发五仓 started + 五仓 completed；断言卡内 `[aria-live]` 恰 1 个、播报文本恒为「当前阶段：并行调研」、且不含步数计数，同时摘要确实变成「5/5 个仓库完成」（证明这些事件确实被处理了，不是「没收到所以没变」）。变异验证：把步数计数拼进 live region 即转红。
residual_human_judgement: 「实听节奏」（读屏是否真的只播一次）未覆盖；用例断的是 live region 的数量与内容稳定性。

### 7. 亮/暗主题下 `skipped` / `unknown` 空心点的可辨识度

expected: 空心与实心的形状差异在两种主题下都能分辨（它是这两态唯一的非文字信号）
requirement: OBS-03
result: [pass]
evidence: `web/tests/e2e/orchestration-observability.spec.ts` —「light / dark 主题下空心点与实心点在 DOM/计算样式层面确实不同」（两个独立 context，`colorScheme` 分别为 light / dark）。断言空心点 `background-color` 为完全透明且 `border-width > 0`、实心点不透明且无边框；同时验证两态各自的 sr-only 文本（「已跳过」/「进度未知」）——形状差异不是唯一信号。变异验证：把两态改成实心即转红。

### 8. 编排完成后的版面：日志组是否给结果让位

expected: 编排完成后时间线收敛成一行、日志组也自动收起，`OrchestratedPlanCard` 留在视口内；用户手动展开日志组后不会被后到的轮询快照再次收走
note: UI-SPEC §C.4 的「整组默认收起」原先未实现，已在 commit `50641583` 补上（判据为所有调研容器到终态，一次性 flag）。此项验证真实多仓场景下的实际版面。
requirement: OBS-02
result: [pass]
evidence: `web/tests/e2e/orchestration-observability.spec.ts` 两条用例：① 终态时时间线标题转「方案编排已完成」、正文收起（卡头一行仍在，不是整块消失）、日志组 `aria-expanded=false`、`OrchestratedPlanCard` `toBeInViewport()`；② `active:true` 让 2 秒轮询持续到达，手动展开日志组后等 5 秒（>2 拍）仍为展开，时间线同理。变异验证：去掉自动折叠 → ①转红；把一次性 flag 换成「每次快照到达都重折」→ ②转红。
found_defect: ②这条用例发现了一个真实缺陷——编排进入终态后轮询会带上收敛令牌（110-MN-02），而 `buildUrl` 把路径里自带的 `?` 编码成 `%3F`，从那一拍起每次 runtime 轮询都 404，`pollConversationRuntime` 的 catch 吞掉异常并停止轮询，界面上表现为「调研日志组突然消失、实时更新静默停摆」。修复见 commit `c09b8018`。
residual_human_judgement: 「真实多仓场景下的实际版面观感」属人判，未覆盖。
