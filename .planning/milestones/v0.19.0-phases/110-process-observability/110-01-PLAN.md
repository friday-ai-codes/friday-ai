## 规划期实读结论（planner 已核验，executor 直接采信，不必重新勘察）

**F-1（决定本 phase 传输设计的硬事实）：chat SSE 流只在编排的前五个阶段开着。**
`chat/conversation_service.py:1681-1768` 实读：SSE 由 `graph.astream(..., stream_mode=["custom","values"])` 的 custom 通道喂给一个 `asyncio.Queue`，消费循环 `yield` 给 `chat/views.py::_stream_events`。编排工具 `start_plan_research` 在 graph 节点内被 await，故 `decompose → route → recall → classify → clarify` 全部发生在**流开着的时候**；到 `research` 挂起后 graph 走 `phase == "waiting"`，流即结束。容器回调经 `subagent/api/callbacks.py:128-145` → `_schedule_chat_plan_resume` 续驱 `research → merge → done`：它跑在**同一个 Django ASGI 进程**里（`subagent/api/callbacks.py:492` 是 `loop.create_task(_resume())`，在回调那次请求的上下文里起的后台 task），但它**不在任何 graph 运行上下文内**，因此**没有任何 SSE 流可推**。
📌 措辞注意：分界不是「另一个进程」，而是「另一个执行上下文 —— 没有 graph 运行上下文」。写成「进程」会让读者以为可以靠进程内共享状态绕过去，而真正的判据是 F-2 那条 contextvar。

⇒ **本 phase 的传输分工是既定事实，不是设计选择**：`process_event` 覆盖前五个阶段的秒级直播；`research → merge` 由既有 2s 运行时快照轮询覆盖（110-02）。这与仓内既有裁定同源——`chat/coding_events.py:1-13` 逐字写着「编码执行在 Runner 容器，回调时 SSE 流已关闭 ⇒ SSE push 与 Runner 容器生命周期根本不兼容」，并正式锁定 ConversationRuntime 快照轮询为该类中间产出的投递路径。调研容器与编码容器是同一种东西，结论照搬。

**不要试图「把 SSE 流撑到编排结束」**（那要改 graph 的挂起语义，是 109 的 spine，本 phase 边界外），**也不要另起一条 WebSocket 推送通道**（`chat/realtime.py::abroadcast_stream` 只镜像 shared 会话、且它自己也只在 SSE 循环内被调用；新起通道直接违反 SC-4「未新建平行推送通道」）。

**F-2：`get_stream_writer()` 可用且天然是本 phase 需要的那把「在不在流里」的开关。**
实测（`server/.venv`，langgraph + Python 3.14）：`from langgraph.config import get_stream_writer` 可导入；在 graph 运行上下文**之外**调用抛 `RuntimeError: Called get_config outside of a runnable context`。它靠 contextvar 传播（Python ≥ 3.11 要求，本仓 3.14 满足），因此在 graph 节点里被 await 的任意深层调用（含 `_emit_event`）都能取到 writer。

🔴 **它不止抛 `RuntimeError`，也会抛 `KeyError`。** 实现是 `get_config()[CONF][CONFIG_KEY_RUNTIME].stream_writer`：`RuntimeError` 只来自最外层的「压根没有 runnable context」；而在「**有** runnable context 但**不是** langgraph runtime」的情形下（例如一条普通的 LangChain runnable 链），`get_config()` 正常返回，随后在取 runtime 键时抛 `KeyError`。
⇒ 本 plan 的 `except Exception` 已经天然覆盖两者（这正是写成 blanket except 而不是 `except RuntimeError` 的理由，别把它「收紧」成具体异常类型）；但用例清单必须把 `KeyError` 那条也列上，否则「收紧成 `except RuntimeError`」这个改动不会有任何测试变红。

⇒ fan-out 不需要自建注册表、不需要把 writer 一路透传穿过 engine/adapter，也不需要显式判断「我是不是 chat 入口」——**取不到 writer 就是没有推送目标**，workflow / MCP / 回调续驱三种情形自动落进静默跳过分支。

**F-3：`_emit_event` 确实是唯一出口，且已有 8 个调用点。**
`transition()`（`:188`，payload 恒空的转移事件）、`_fail()`（`:272`）、`builtin_processes.py:179/192/214`、`clarify_adapter.py:263`、`research_adapter.py:232/248`、`architect_merge_adapter.py:434`、`clarification_service.py:195`、`spec_generation.py:163`、`callbacks.py:1776/1788/1821`。挂在 `_emit_event` 一处即全覆盖。

**F-4：`build_envelope()` 自己取 `timezone.now()`，与落库行的 `ts` 默认值是两个不同的瞬时值。**
`event_taxonomy.py:133` 是 `"ts": timezone.now().isoformat()`；`ConvergenceSessionEvent.ts` 的 default 也是 `timezone.now`，在 `objects.create()` 时另取一次。两者相差微秒级。
⇒ 若直接用 `build_envelope()` 的 ts 出网，前端按 `(event, ts, …)` 去重时 **SSE 那条与快照那条永远算作两条不同事件**，调研完成数 / 融合轮次 / 澄清轮次这三个计数类摘要会**成倍虚高**。这是本 plan 最容易被忽略、且症状最像「前端算错了」的坑。**必须由落库行回填 ts**（Task 2 第 4 点）。

    **2. `compress_failure_reason(error: Any) -> str`**

    把 `ConvergenceSession.error` 压成闭集，返回值恒 ∈ `{stage_exception, merge_validation_exhausted, clarification_timeout_no_answer, advance_step_limit, unknown_process_type, unknown_stage, unknown}`：

    ```
    error 非 dict                      → "unknown"
    error["reason"] ∈ 闭集              → 直取
    ```
