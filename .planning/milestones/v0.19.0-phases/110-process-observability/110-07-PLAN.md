## 规划期实读结论（planner 已核验，executor 直接采信）

**F-17（🔴 UI-SPEC 的一条 Covered 项已过期，必须显式退役）：`orchestratedPlanData` 早已不是 `.find` 了。**
UI-SPEC §落点 F 与 §UI Considerations 第 17 条要求「把 `.find` 加固为末位终态匹配」。但 UI-SPEC 定稿之后、109 的代码评审修复轮里，这一处已经被改成**按 `item.result` 逐条解析**：`ChatMessageBubble.vue:797-822` 是 `function resolveOrchestratedPlanData(result: unknown)`，模板 `:1263` 调用 `resolveOrchestratedPlanData(item.result)`，函数注释里逐字写着「🔴 必须按**传入的那一条** tool call 解析，不能在 toolCalls 里 find 第一条编排工具」。

⇒ **本 plan 显式退役 UI-SPEC Covered #17**：不做「末位终态匹配」这类改造，也**绝不**把取数改回任何形式的 `toolCalls.find`。逐条解析比「找最后一个终态」更强（它对每个气泡各自成立，而不是对整条消息挑一个），退回去就是把 109 修好的缺口重新打开。本 plan 的义务是**加一条回归锁用例**，让将来任何往 `.find` 方向的「简化」立刻变红。

> 注：`codingPlanData`（`:825`）仍是 `.find` 形态，那是 109-REVIEW LO-02 记录的已接受债务，**本 phase 不动它**（范围外，且两处应当一并处置而不是各改一半）。

**F-18：`plan_research_sessions` 与 `DeepAnalysisSession` 的形状差一层适配。**
`DeepAnalysisCard` 的 `session` prop 类型是 `DeepAnalysisSession`（`{session_id, task_description?, status?, progress_message?, progress_percent?, logs}`），而 `PlanResearchSession` 是 `{session_id, plan_session_id, repository_id, repository_name?, status?, logs}`。`logs` 两侧都是 `DeepAnalysisLog[]`（形状逐字同源，`decorateDeepLog` 可零改动解码）。
⇒ 只需在日志组里做一次浅适配（`{ session_id, status, logs }`），`taskLabel` 传仓库名即可覆盖头部标题（`DeepAnalysisCard.vue:40` 的 `props.taskLabel || session.task_description || '执行记录'`）。**`DeepAnalysisCard` 零改动**。

**F-19：`repoNames` 现成。**
`ChatMessageBubble.vue:407-410` 已有 `repository_id → name` 的 computed（源自 `repositoriesStore`）。日志组按 UI-SPEC §A.4 的解析顺序用它做第二级兜底。

**F-21（🔴 本 plan 最容易漏、且今天零测试覆盖）：`planResearchSessions` 没有会话维度，日志组的挂载条件必须自己补上。**
两块新 UI 的「不重复」保护强度**并不对等**：
- 时间线取 `orchestrationSessions[sessionId]`（110-04 按 `session_id` 分桶），换一个 sessionId 就是换一个桶，**天然自限**。
- 日志组取的 `planResearchSessions` 是 110-04 里的一个会话级扁平 `ref<PlanResearchSession[]>([])`，**每份 runtime 快照整体替换它**（110-04 Task 2 D 节：`planResearchSessions.value = runtime.plan_research_sessions ?? []`，全量列表语义），而 110-03 的后端分支只取**本对话最近一次** `ConvergenceSession` 的容器。

⇒ 一段对话里跑两轮编排时，快照里装的是**第二轮**的容器，而第一条编排消息的气泡若只按 `isOrchestrationTool && item.id === lastOrchestrationToolItemId && planResearchSessions.length > 0` 挂载，它会**照样渲染**——用户看到两处「方案调研 · N 个仓库」，其中一份挂在了错误的方案上。这与本 plan must_have 「同一进度不出现两遍」是同一类缺陷，但那条只覆盖**消息内**重复，Task 3 原有的用例又全是单消息场景，所以**没有任何一条会变红**。

⇒ 材料是现成的：110-03 Task 2 给每条 `PlanResearchSession` 都带了 `plan_session_id`（`= str(ConvergenceSession.id)`），与本 plan A 节 `orchestrationSessionIdFor(item)` 解析出的会话 id 同源同值。挂载前按它过滤即可（Task 2 B 节）。

**F-20（边界，不得越过）：`RoutingDecisionPanel` 在 SPA 里没有挂载点，且有一条锁它不渲染的测试。**
实读：`web/src/**/*.vue` 里零个 `<RoutingDecisionPanel />` 使用点；`web/src/components/chat/__tests__/partsApiIntegration.spec.ts` 有一条锁「该面板不渲染」的用例。
⇒ 本 plan **不挂它、不改它、不让那条锁变红**。它导致 ROUTE-01/02 与 RELY-03 的用户可见半边当前不可达，属**里程碑级缺口**，已单独向用户上报，**不并入 Phase 110 的范围**；VERIFICATION 需如实记录（见 `<assumptions>`）。

    新增 `function planResearchSessionsFor(item): PlanResearchSession[]`：

    const sid = orchestrationSessionIdFor(item)
    return sid ? chatStore.planResearchSessions.filter(s => s.plan_session_id === sid) : []

    理由（写进注释，且必须点名它与时间线的**不对等**）：时间线取的是 `orchestrationSessions[sessionId]`，按 session 分桶 ⇒ 换 session 即换桶，天然自限；而 `planResearchSessions` 是**会话级的扁平数组**，每份快照整体替换它、且后端只装本对话**最近一次**编排的容器。⇒ 一段对话里跑两轮编排时，若不按 `plan_session_id` 过滤，第一条编排消息会渲染出第二轮的日志组——用户看到两份「方案调研 · N 个仓库」，其中一份挂在错误的方案上。
