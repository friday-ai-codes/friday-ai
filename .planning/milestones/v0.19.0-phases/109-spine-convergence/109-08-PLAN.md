    4. 用 `AlertDialog` 家族（**不是**普通 `Dialog` —— 阻断式风险确认需要焦点陷阱与显式取消）。**不复用** `GlobalConfirmDialog` / `useConfirmDialog`：其 `ConfirmOptions` 只有 `title / description / confirmText / cancelText / variant`，无法承载必勾 Checkbox，为它加字段会改动一个被 20+ 处复用的全局组件。⇒ 在本组件内局部落一个 `AlertDialog`。

    6. **确认按钮不用 destructive 配色**：送编码不销毁数据、不可逆性有限（产出 PR，可关闭）；风险语义由 amber 风险块 + 必勾 Checkbox 承担已足够，染红会稀释 destructive 在别处的信号强度。

    8. **三条触发路径**（UI-SPEC §C.1）：
       - 创建态内嵌 selector 确认（`handleMultiConfirm`）→ 走弹层；
       - 追加态 Dialog 确认（同一 `handleMultiConfirm`）→ 天然覆盖；
       - **单仓重试**（`handleSessionRowRetry` → `retrySingleRepository`）→ **同样走弹层**。理由：服务端 gate 落在 session **创建**上，重试同样创建 session ⇒ 服务端会一致地拒绝；若前端因「用户之前已确认过」而自行补 `true`，等于前端替用户签名。
       - legacy 单仓 `handleConfirm`（`:294`，仅 `codingPlanId` 缺失时可达）→ **不覆盖**（此时前端拿不到 `provenance`、服务端也无 `plan_id` 可判定；且它确认的是**已存在**的 session，而 gate 落点是 session 创建）。在代码注释里写明这条边界与理由。
       实现建议：把「是否需要先确认」抽成一个内部函数 `ensureUnresearchedAcknowledged(): Promise<boolean>` —— `isUnresearched === false` 时直接返回 `true` 且**不打开弹层、不发送字段**；否则打开弹层并等待用户选择，确认返回 `true`、取消返回 `false`。两个入口（多选确认 / 单仓重试）都先过它。
    9. 🔴 **不可协商的不变量**：`acknowledge_unresearched: true` 只能由用户在弹层里勾选 Checkbox 后产生。不缓存、不记忆、不因「刚才确认过」而复用。**前端在任何代码路径下都不得自行填该值。**
