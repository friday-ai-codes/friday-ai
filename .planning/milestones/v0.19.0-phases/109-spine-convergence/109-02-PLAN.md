    在 `CodingPlan.Meta` 追加 `constraints`（该 Meta 目前 0 个约束）：
    ```
    models.UniqueConstraint(
        fields=["source_artifact_version_id"],
        name="uniq_codingplan_source_artifact_version",
    )
    ```
    🔴 **必须是无条件约束，不得带 `condition=Q(source_artifact_version_id__isnull=False)`**。理由是一条实证的静默失效：`django/db/backends/mysql/features.py:48` 是 `supports_partial_indexes = False`，而 `django/db/backends/base/schema.py:1792-1793` 的 `_unique_supported()` 在 `condition` 非空且后端不支持 partial index 时返回 `False` ⇒ **`AddConstraint` 被静默跳过、不报错也不告警**。本仓 `server/friday/settings.py:447-458` 明文支持 `mysql://` 与 MariaDB ⇒ 一旦带 `condition`，MySQL 部署上这条约束根本不存在，SC-4「同一方案版本重复投影不产生重复编码计划」在并发下失效，109-03 的 `except IntegrityError` 分支永不触发，109-05 的 `arebind` 会静默改写他人投影而非 fail-closed。

    在约束旁写注释说明两点：① **PostgreSQL / MySQL / SQLite 的唯一索引都把 NULL 视为互不相等**，因此草稿行与存量行（该列为 NULL）天然不受唯一约束限制，无需 `condition` 即可多行共存 —— 加 `condition` 只带来 MySQL 静默失效，不带来任何额外能力；② 按 `coding_session_service.py:37-47` 的既有纪律，本约束名与 service 层的幂等分支字面一致。约束**不纳入** `conversation`（同一 `ArtifactVersion` 在两个 conversation 各投一份正是要防的重复）。

    在 `server/tests/test_coding_plan_model.py` 追加两条断言，把「约束被后端静默跳过」变成可检出的缺陷：
    - **约束存在性断言**：用 `django.db.connection.introspection.get_constraints(cursor, CodingPlan._meta.db_table)` 取回约束字典，断言存在一项 `unique is True` 且其 `columns == ["source_artifact_version_id"]`（约束名在部分后端会被改写，故按列集合而非按名字断言；若后端保留名字则一并断言 `uniq_codingplan_source_artifact_version` 在键集合中）。注释写明：这条断言存在的唯一理由是 partial index 在 MySQL 上会被静默跳过 —— 没有它，「约束不存在」和「约束存在」的测试表现完全一致。
    - **多 NULL 行共存断言**：连续建两条 `source_artifact_version_id` 为 NULL 的 `CodingPlan` 均成功（证明无条件约束不误伤草稿行），再建两条同一非空取值 → 第二条抛 `IntegrityError`（证明约束真的在挡）。
