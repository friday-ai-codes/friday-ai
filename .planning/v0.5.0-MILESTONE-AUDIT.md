## 跨阶段集成发现

审计重点是连接而非存在性。五条关键 contract 全部经源码 grep + 测试链路坐实：

### 1. 单一排除匹配器是真正被复用的共享 chokepoint（无重写 / 无旁路）

`server/services/exclusion.py` 是排除判定唯一事实源，下游 4 个阶段全部 `from services.exclusion import ...`，无任何阶段自己另写过滤逻辑：

- **23（purge/reconcile）**：`purge_reconcile.py:41,119` 复用 `build_matcher_for_repo`；degraded 仅反映构造期失败，不谎报已一致。
- **24（detection baseline + accept→rule）**：`sensitive_detect.py:35,200` 复用 `BUILTIN_GLOBAL_DEFAULTS` 作文件名启发式基线；accept 经 `views.py:1372` 建 `RepoExclusionRule(source=ai_suggested)` 后 `invalidate_matcher_cache` —— 检测产物回灌成同一匹配器的输入。
- **25（commit 摘要 + chunk-at）**：`commit_index.py:30,319,326` 经 `build_matcher_for_repo` + `_filter_changed_files` 过滤变更路径；`chunk_lookup.py` 同源 fail-closed。
- **26（多仓检索）**：MCP 多仓不另写过滤，经 `HybridSearchService → search_rag`，由 `rag_search.py:85` 逐仓 `build_matcher_for_repo` 兜底。

判定异常 / 构造失败一律 fail-closed（matcher 内部 return True；rag_search 整仓丢弃；reconcile 置 degraded 并中止清理）。INV-4 在跨阶段层面成立。

### 2. detect → confirm → exclude → purge 端到端流闭合

`sensitive_detect`(24) 产 `SensitiveFileSuggestion` → 用户 accept(24 API) → `RepoExclusionRule(ai_suggested)`(22 模型) → 该规则进入 `_resolve_effective_specs` 合并 → `compute_reconciliation`(23) 用同一 matcher 识别为差异文件 → `run_cleanup → purge_file`(23) 删净五面。链条无断点，且**严格区分"建议/确认"与"删除"**：accept 路径无任何 `CleanupRun`/`purge`，删除必须用户在对账面板显式触发（EXCL-03「不静默删除」与 EXCL-04/05 清理解耦但可衔接）。

### 3. search_rag 单 chokepoint 一致性

`rag_search.py:search_rag` 是唯一 RAG 主线检索入口：22 在此逐仓过滤；25 的 commit 文档以合成 `file_path=.friday/commits/{sha}`（不被排除）入主 collection，经同一入口自然召回，无需旁路；26 多仓只是对同一 chokepoint 的 `repository_ids` 扩展迭代，每仓独立 matcher。三阶段共用一条收集 + 去重 + fail-closed 路径，未分叉。

### 4. purge_file 与索引删除路径收敛（PF-03/PF-05）

`server/services/purge.py:purge_file` 是三条删除路径（indexer 两条 DELETE 分支 + Phase 23 run_cleanup）的唯一派生数据删除点，覆盖 Qdrant 主+overlay(PF-05)/FileIndex/ChunkRegistry(经 pre_delete 信号联动 ChunkEdge)/codegraph 五面。indexer 冗余 FileIndex 删除循环已移除，PF-03 收口；ChunkRegistry 走 queryset `.adelete()` 不绕过信号。

### 5. 凭证解析器统一（REPO-01 D-02）

`aresolve_git_token` 接入 indexer/repo_mirror/graph_builder/merge_request_service/mr_service/coding/coding_session_service/diff_archive/pr/coding_graph/code_review/summary_service/chat_tools/views 全部取 token 站点；非测试代码中内联 `decrypt_value(...encrypted_token)` 仅剩解析器自身。实例池-only 仓库可在所有路径复用同一 host 凭证，per-repo token 仍优先（向后兼容不回退）。

## 技术债 / 延后项

均为**非阻断**，符合里程碑范围与 autonomous 模式约定：

1. **前端浏览器 UAT（延后，非阻塞）**：排除规则编辑面板、对账/清理面板、AI 敏感建议面板、`/admin/git-credentials` 管理页的真实浏览器视觉与端到端交互核对。四面板均已实现且有 vitest 守护测试通过，仅缺人工视觉确认。
2. **REQUIREMENTS.md 复选框**：v1 需求 EXCL-01..06 / IDX-01..02 / REPO-01..02 现均为 `[x]`（23-VERIFICATION 曾记 EXCL-04/05 未回填，现已勾选），与实现一致。
3. **设计内 Out-of-Scope（非债务，文档化 caveat）**：git object 物理抹除（backlog，安全边界定为"Friday 不可见"不承诺 git 历史物理消失，敏感清理已诚实上报 unscrubbed/caveat）；片段→需求反查（依赖 IDX-02，规划 v0.6）；全量操作审计（v0.10，本里程碑仅埋排除/清理审计点 `exclusion.blocked`/`purge.started`/`purge.completed`）。
4. **已声明的缓解非根除点（已文档化，非缺口）**：`is_redos_risky` 启发式可能漏报隐蔽 ReDoS 形态；敏感清理对无 file 关联面做子串脱敏并诚实标 `UNSCRUBBED_PLANES`，不假装清除 git/备份。
