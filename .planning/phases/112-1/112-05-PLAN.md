## 五动作 → 重调研的闭合链路（B1 / ROADMAP SC-4）

SC-4 要求「用户移除仓、手动加仓（触发新仓调研）、改判 role、修改职责均驱动对应重调研」。本 plan 必须把这条链**首尾接通**，缺任一环 SC-4 即不可能为真：

| 动作 | 是否重调研 | 确定规则与实现动作 |
|---|---|---|
| `add_repo` | **是** | 新仓无任何 fitness → `apply_gate_action` 经 `ResearchService.create_tasks_for_session(session, [{"repository_id": ..., "routed_confidence": "low"}])`（幂等 get_or_create，落 `PENDING`）+ 快照该仓 `pending_research=True` |
| `remove_repo` | **否** | 仅收窄仓库集，既有结论不失效；只改快照 + `record_answer` 留痕（并产 boundaries 草案） |
| `reclassify_role` | **仅 indirect→direct 时是** | 深调研结论是轻量合成的超集：`indirect→direct` 需要容器级 fitness → `await ResearchService().mark_stale([task.id])`（`STALE` 在 112-04 的 `_DISPATCHABLE_STATUSES` 内）+ 快照 `pending_research=True`；`direct→indirect` 与同角色改判 → 否（已有深调研结论足够） |
| `edit_responsibility` | **仅 payload `rerun is True` 时是** | 职责文本变化是否改变调研范围无法机械判定 → 不猜：默认否（只更新快照），**只有调用方显式传 `rerun=true`（用户在 UI 勾选「重新调研该仓」）才** `mark_stale` + `pending_research=True` |
| `confirm` | 否 | 走锁定路径 |

链路四环（**必须同时存在，否则动作只改快照就断了**）：
1. **写标记 + 置可派发态**：`apply_gate_action` 按上表处理（见 Task 1 ②）。
2. **出边**：`repo_confirmation` 的 transitions 含 `{"research_required": "repo_research"}`，`_h_bp_repo_confirmation` 检出待调研标记时返回 `event="research_required"`（见 Task 3 ①）。
3. **增量派发**：`_h_bp_repo_research` 复用 112-04 的增量 `dispatch`（候选来源含 `stage_state["confirmation"]` 的 `pending_research` 仓，只派发 `PENDING`/`STALE`，已完成仓不重跑）。
4. **续驱触发（第 2、3 环的引擎）**：动作端点只落库不推进 stage，所以必须有人调 `engine.advance`。**触发点定在视图层**（Task 2 ⓐ）：动作持久化成功后（`confirm` 在 `alock` 之后）调 `blueprint_resume.aresume_after_gate_action(session, initiated_by_user_id=...)`。
   - **为何是视图层而非 `apply_gate_action` 内**：`confirm` 的实际锁定由视图在 `apply_gate_action` 返回 `ready_to_lock=True` 之后调 `alock` 完成——若把续驱塞进 `apply_gate_action`，`confirm` 会在锁定**前**续驱，确认门线程仍 open，只会 self-loop 空转一步，`confirmed` 边永远走不到。视图层是唯一知道「本次动作（含锁定）全部持久化完毕」的位置，六个端点共用同一个 helper 调用，形状一致。
   - **失败隔离**：`aresume_after_gate_action` 内部 `try/except Exception` 全兜（helper 自己兜，视图不需要重复包），失败只记 `blueprint_gate_resume_failed`（`category="caller"`、异常文本经 `redact_secrets_in_text`）**并正常返回**——动作本身已持久化，REST **绝不因续驱失败回 5xx**。`pending_research` 标记与 task 状态都在库里，下一次任意确认门动作或容器回调 barrier 续驱时判据依旧成立，不丢事。
   - **并发/幂等零新造**：并发续驱由 `ConvergenceSessionService._apply_transition_sync` 的 CAS 天然去重（`filter(id=..., current_stage=from_stage).update(...)`，`updated != 1` → `ConcurrentTransitionError`，engine 已吞掉并记 sampling 日志、绝不落 fail，见 RESEARCH 主题 2.4）——同一会话并发续驱只有一方赢得转移，败者那步 advance 是 no-op；容器不重开由 `dispatch` 的 `_DISPATCHABLE_STATUSES` 白名单 + `create_tasks_for_session` 的 `get_or_create` 保证；死循环由 `max_steps=20` 兜底。**不新增锁、不新增字段。**
   - **pause 判据必须放行这一步**：`repo_confirmation` 挂起时确认门线程恒为 open+blocking，若续驱沿用「有 open+blocking 线程就短路」会在 advance 之前直接返回，`research_required` 边永远走不到（这正是本环最容易断的地方）。故 `waiting_clarification` 短路条件收紧为「有 open+blocking 线程 **且** `acollect_pending_research_repos(session)` 为空」（Task 3 ②），与 handler 判据同一份实现。
