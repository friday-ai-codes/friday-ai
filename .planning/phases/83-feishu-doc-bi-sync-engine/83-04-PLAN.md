交付 SYNC-04（并强化 SYNC-03）冲突处理全集：区段所有权分区 + Agent append + 三方合并 + capture-never-clobber + 编辑感知延迟写 + 乐观并发 rebase——保证"用户在飞书编辑中系统写入绝不冲掉用户内容"。

四机制叠加（CONTEXT 锁定）：①block 级写（83-03 已落）；②区段所有权分区（pull/push 强制 section 边界）；③Agent 写一律 append 新 block（MEMORY/AI 待确认区落实 append）；④编辑感知延迟写：push 前探测 `last_feishu_edit_at`，活跃→重排 run_at；带乐观并发（重拉飞书 revision，!= last_synced → 先 pull rebase 再 push）。

同块真冲突（base≠theirs 且 base≠ours）→ `three_way_merge`（83-01）：不相交自动并；相交飞书侧（theirs）优先保留为 merged，落败的系统/DB 侧（ours）经 `capture_block_revision` 落 `ProjectDocBlockRevision`（MEMORY 落 `ProjectMemoryRevision`）+ 飞书评论提示 + 标记，**绝不静默丢**。

OQ 裁决：
- OQ-1：MEMORY 非成员飞书编辑 → 受限 sync 入口 fail-soft 接受、归因（system/未映射）、落 revision/草稿，**不进 active ProjectMemory**；前端贡献仍 MEM-02 fail-closed。
- OQ-2：STATE/MILESTONES/RESEARCH/PREFLIGHT 落败方 → `ProjectDocBlockRevision`（83-01 已建表）。
- OQ-3：编辑感知探测数据源 = DB `ProjectDoc.last_feishu_edit_at`（drive 事件到达时更新），push 前比对。

Purpose: 把"防冲突"从机制承诺落成可测代码，保证 capture 有落点、rebase 不依赖真实 doing lock（Pitfall 3）。
Output: pull 冲突三方合并接管、capture_block_revision writer、MEMORY 受限 sync 入口、push 编辑感知延迟 + rebase、可选飞书评论、冲突/rebase 单测。
</objective>
