② 取图时 `seed_symbol_ids=[source_sid, target_sid]`（两端都是种子，D-24），`depth` 传一个足以覆盖最短路的值——用 `_TRACE_SEED_DEPTH: Final[int] = 3`（模块级常量，注释写明：子图路径按 `radius = depth + 1` 扩张，3 已能覆盖绝大多数「两个符号之间几跳」的实际查询；更深的路径在按需子图上可能查不到，这一点在无路径结果里如实声明）。
③ 调 `trace_path(graph.graph, source_sid, target_sid, min_confidence=..., alt_path_cap=...)`。
④ 信封：
```
{"ok": True, "tool": "trace_call_path", "repository_id": ..., "branch": ...,
 "query": {min_confidence, include_low_confidence, alt_path_cap},
 **trace_path 的全部返回字段（found / reason / source / target / path / hops / path_confidence /
   equal_length_path_count / equal_length_path_count_capped / alternatives_note）,
 "staleness": ..., "graph": degradation_payload(graph.meta)}
```
🚨 `found is False` 时 `ok` 仍为 `True`——「确实没有调用关系」是一个**成功的查询结果**，不是失败（D-20）。这两个布尔的区别必须写进 docstring：`ok` 回答「这次查询做成了吗」，`found` 回答「两点之间有路吗」。⛔ 把 `found=False` 映射成 `ok=False` 会让 agent 把「没有调用关系」误读成「工具坏了」，正是 D-20 要防的事。

⑤ 当 `graph.meta.degraded` 以 `"on_demand_subgraph"` 开头且 `found is False` 时，在 `graph["declarations"]` 里追加一条补充声明：「本次在按需子图上查询，超出子图覆盖范围的更长路径可能未被检出」——⛔ 不编造「确实无路径」这个更强的结论。
