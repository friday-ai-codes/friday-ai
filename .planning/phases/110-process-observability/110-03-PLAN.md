## 规划期实读结论（planner 已核验，executor 直接采信）

**F-5（会踩空的陷阱）：plan_research 的 `AgentSession.metadata` 里没有 `conversation_id`。**
`research_adapter.py:180-196` 实读：`AgentSession.objects.acreate(metadata={"source": "plan_research", "plan_session_id": str(session.id)})` —— **只有两个键**。而 deep analysis 分支的归属谓词是 `main_session__metadata__conversation_id=conversation_id`（`conversation_service.py:2462-2465`）。
⇒ **照抄 deep analysis 的写法会得到一个恒空的查询集**：不报错、不变红、只是日志永远不出现，而症状与「后端没写日志」完全一致。归属链必须改走 `ConvergenceSession.conversation_id`（模型上的 `UUIDField(db_index=True)`，由 `start_orchestration` 服务端写入，客户端不可控），见 Task 2。

**F-6：`SubAgentSession.last_output` 同时带三个绑定键。**
`last_output = {"source": "plan_research", "plan_session_id": <ConvergenceSession.id>, "research_task_id": …, "repository_id": …}`，日志由 `runners/consumers.py::_append_runtime_log`（source-agnostic，最多保留 80 条 `_MAX_RUNTIME_LOGS`）追加到同一个 `last_output["logs"]`，形状 `{type, content, ts}` 与前端 `DeepAnalysisLog` 逐字同形。CONTEXT §Claude's Discretion 要求 planner 实读确认绑定键 —— **确认为 `last_output.plan_session_id`**，定版。

**F-7：runtime 端点直出 dict，没有 serializer 过滤。**
`chat/views.py:1039-1040` 是 `runtime = await ConversationService.get_conversation_runtime(...)` + `Response(runtime)`。⇒ 新增键无需登记任何 serializer；**反过来说，任何塞进 dict 的东西都会原样出网**，泄漏面控制只能在本函数内做。

**F-8：`runtime["active"]` 在编排在途期间为 true，不必也不应改动它。**
`:2315-2330` 实读：`active` 由最近一条 `OrchestrationRun` 的 status 决定，`RUNNING` / `WAITING` ⇒ true。编排挂起在 research 时 graph 走 `phase == "waiting"`，run 停在 `WAITING` ⇒ `active` 为 true ⇒ 前端 `pollConversationRuntime` 持续轮询（`stores/chat.ts:1049-1077`）。
⚠️ **但编排终态那一拍 `active` 会变 false**，而前端现有代码只在 `active === true` 时才 `applyRuntimeSnapshot` —— 终态的 `orchestration`（`done` / `failed` + reason_code）会因此**永远到不了 store**。这一半的修复属于前端（110-04 Task 2 的 `applyOrchestrationRuntime` 必须在两个分支上都调用）。**本 plan 不改 `active` 的语义去迁就它**：`active` 是「这条对话还在跑吗」，不是「时间线还要不要更新」，把两者混起来会污染既有的 deep analysis / coding 判定。
