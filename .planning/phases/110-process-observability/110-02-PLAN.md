<objective>
把 `SubStepTimeline` 做**纯加性**泛化，让它同时服务工作流执行面（`ExecutionNode`）与本 phase 的编排阶段时间线，兑现 CONTEXT 的硬约束「不新增组件原语、不新增色板与字号」。

Purpose: UI-SPEC §交互契约 A.2 实读后给出结论「原样不能用，但它是正确的复用对象」，并列出 5 处缺口（类型硬绑 `SubStep`、只有 4 态无 `skipped`、摘要行写死 `output_data.error` 且仅失败时渲染、每行强制可点、状态只由圆点颜色传达）。UI-SPEC 同时把「泛化共享组件 vs 在 chat 下新建一个逐字复制同款 DOM 的本地组件」列为 Unresolved #3，要求 planner 二选一而不是留给 executor 现场发挥 —— 见下方 `<decision>`。
Output: `TimelineStepItem` 类型、泛化后的 `SubStepTimeline`、以及一个从零建起的 spec（该组件今天**没有任何测试**，泛化前先把既有行为锁住）。
</objective>

<decision>
## 二选一裁定：采「加性泛化共享组件」，不新建 chat 本地副本

**裁定：泛化 `web/src/components/execution/dag/SubStepTimeline.vue`。**

理由三条，按分量排序：

1. **5 处缺口全是通用时间线关注点，不是 chat 专属逻辑。** 摘要行、跳过态、只读模式、行尾角标、可读状态文本——把它们叫做「chat 的需求」是错的，它们是「一个竖向步骤时间线本该有的能力」。`ExecutionNode` 侧同样受益（`role=list` 语义与 sr-only 状态文本对它是净改进）。承载通用关注点不构成「共享组件被两个域的关注点污染」。
2. **副本方案的代价是不可见的那种。** 逐字复制同一套 DOM 与类名意味着此后每一次视觉调整（间距、连线定位、状态点尺寸）都要人肉同步两处，而漏同步**不报错、不变红**，只是两个页面慢慢长得不一样。本里程碑已经两次被「不报错的静默漂移」咬过（109 的 `UNGROUPABLE_TOOLS` 与 `plan_id` 守卫），不再制造第三处。
3. **加性改动的回归面可被机械封死。** 全部新增项都是可选 props / 可选字段，`SubStep` 结构上天然满足 `TimelineStepItem`，`ExecutionNode.vue:340` 的调用点一个字都不用改。本 plan 用一组显式的「ExecutionNode 既有用法」用例把这一点钉死（该组件今天零测试，泛化前先补锁是本 plan 的第一件事）。

**同时结掉 UI-SPEC Unresolved #5（状态色 map 的位置）**：`skipped` / `unknown` 两个分支**并入组件内既有的那份 `stepStatusColor` map**，不迁 `~/config/status.ts`（那份配置服务于 `StatusBadge` 的 5 个 `type`，塞一个时间线专用点色 map 进去是更差的耦合），也**绝不在 chat 侧另起第二份**。形式上违反 DESIGN.md「禁止组件内定义 statusColors」这条记为既有技术债，本 phase 不扩大它、也不新增第二处。
</decision>

     * 通用竖向时间线 item 契约（SubStepTimeline 的入参单元）。

     * 与 `SubStep` 解耦：`SubStep` 带 step_type / step_order / input_data / started_at 等

    export interface TimelineStepItem {
      id: string
      name: string
      status: 'pending' | 'running' | 'completed' | 'failed' | 'skipped' | 'unknown'
