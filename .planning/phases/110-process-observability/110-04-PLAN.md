## 规划期实读结论（planner 已核验，executor 直接采信）

**F-9（本 plan 最容易漏、且症状是「跑完什么都没有」）：`applyRuntimeSnapshot` 只在 `runtime.active === true` 时被调用。**
`stores/chat.ts:1043-1122` 实读：`pollConversationRuntime` 拿到 runtime 后先判 `if (runtime.active) { applyRuntimeSnapshot(runtime); …; scheduleRuntimePoll(id); return }`，非活跃分支**完全不碰** `applyRuntimeSnapshot`，直接停轮询 + `hydrateConversationMessages`。
而编排终态那一拍（`OrchestrationRun` 走到 COMPLETED / ERROR）`active` 恰好变 false。⇒ 若把编排快照的应用挂在 `applyRuntimeSnapshot` 里，**`done` / `failed` 这两个最需要被看到的状态永远到不了 store**，时间线会永远停在最后一个在途阶段。
⇒ 必须新建一个独立的 `applyOrchestrationRuntime(runtime)`，并在 `runtime.active` 分流**之前**调用一次（两条分支自动都覆盖）。

**F-10：`applyRuntimeSnapshot` 的第一行就是 `isStreaming.value = true`。**
`:849-851`。它是「恢复一次进行中的流」的语义，不是「刷新一份只读快照」。⇒ 编排状态**绝不能**并进它 —— 在非活跃分支调用它会把输入框错误锁住。这条同时解释了为什么 F-9 的解法是「新函数」而不是「把调用挪到分流之前」。

**F-11：`handleSSEEvent` 已有两道前置守卫，新 case 放进 switch 即自动继承。**
`:1501-1528`：① 前台守卫（`ownerConversationId !== currentConversationId` ⇒ 只更新列表标题后 return），② 中断守卫（`streamingStatus === 'interrupted'` ⇒ 除 `message_complete` 外全丢）。
中断后丢弃 `process_event` 是**正确行为**：用户已中断，实时进度不该继续写 UI；而真实进度仍会由 2s 快照补齐。**不要为 `process_event` 开这两道守卫的后门。**

**F-12：旁观者链路自动获益，零额外接线。**
`chat/realtime.py::abroadcast_stream` 把 SSE 事件逐条镜像给共享会话的旁观者，前端在 `:2877` 用 `handleSSEEvent(payload)` 消费同一套分发。⇒ `process_event` 进 switch 后，共享会话的旁观者也能实时看到编排进度，本 plan 不需要为此写任何代码。
