## 规划期实读结论（planner 已核验，executor 直接采信）

**F-13：阶段推进的骨架来自「转移事件」，阶段摘要的内容来自「领域事件」，两类都从同一条 `process_event` 通道来。**
`convergence_session_service.py:188` 实读：每次 `transition()` 都会额外 emit 一条**转移事件名**，`payload` 恒为空 dict。`builtin_processes.py:270-315` 的 7 个 `StageDef.transitions` 给出全部转移事件名与它们指向的目标 stage：

| 转移事件 | 会话推进到 |
|---|---|
| `decomposed` | `route` |
| `routed` | `recall` |
| `recalled` | `classify` |
| `classified` | `clarify` |
| `clarified` | `research` |
| `needs_clarification` | `clarify`（自环） |
| `research_dispatched` | `research`（自环） |
| `research_complete` | `merge` |
| `merged` | `merge` + 会话 `done` |
| `validation_failed_reclarify` | `clarify`（**回退**） |
| `validation_failed_reresearch` | `research`（**回退**） |
| `exhausted` | `merge` + 会话 `failed` |
| `process.session.failed` / `fail` | 任意 stage → `failed` |

🔴 **注意存在回退转移**（融合校验不过会退回 clarify 或 research）。⇒ 临时指针必须取**按 ts 排序后最后一条**可识别转移事件所指向的 stage，**不能取「见过的最大序号」** —— 后者在回退后会把时间线卡在 merge，而实际会话已经回到 clarify，那正是「时间线撒谎」。

**F-14：「拆分」这一步在事件流里是哑的。**
`_h_decompose`（`builtin_processes.py:60-107`）只打 `logger.info`，**不 emit 任何领域事件**；需求点条数只在 `stage_state.decomposition.segments` 里。⇒ 「拆分」能从 `decomposed` 转移事件拿到**状态**，但摘要只能来自快照的 `segment_count`（110-03 已透出）。这意味着刚发起编排的头 2 秒（第一次轮询到达前）拆分步有状态无摘要 —— 这是**预期行为**，不要为它造假数据。

**F-15：`classify` 的可见性有两个来源且是「或」关系。**
`has_classify`（快照，后端从 `decomposition.mode` 派生）**或** 见过 `technical_plan.feature.classified` 事件。后者是兜底：快照未到时靠事件判定。
边缘情形：feature_list 流程但 `deps.classify` 未注入（`builtin_processes.py:208-210` 的 pass-through）⇒ 有 `has_classify` 但无领域事件 ⇒ 该步走 `complete` + 摘要留空，**不标 `skipped`**（它确实穿过了，只是没产出内容）。

**F-16：`repo.routing` 的 `candidates` 与调研的 repo 数不是一回事。**
路由候选里 light path 的仓不会起调研容器。⇒ `{done}/{total}` 的 `total` 必须取 `repo.research.started` 的去重 `repo_id` 数（实际派了几个容器），取候选数会让进度永远到不了满（UI-SPEC §Backstop 第 8 条）。

**F-16b（明文裁定，不得静默改写）：融合轮次继续按 `Set<ts>` 数，不给 `merge.started` 的 payload 加 `attempt`。**

事实：`architect_merge_adapter.py:199` 已经算出 `attempt = await ArchitectMerge.objects.filter(session_id=...).acount()`（本次是第几轮），但 `:204-208` emit `EVENT_PLAN_MERGE_STARTED` 时 payload 只带 `{"partials", "extra_evidence_count"}`，**没有把它带上**。把 `attempt` 加进 payload 是一行改动，能让轮次不再依赖 `ts`。

**裁定：不加。** 理由按分量排序：

1. **本 plan 唯一依赖 `ts` 的这个计数，其实不经过跨链合流。** 110-01 F-1 已定死：SSE 只覆盖编排的前五个阶段，`research → merge` **只**由 2s 运行时快照投递。⇒ `technical_plan.merge.started` 根本不会同时从两条链到达，`Set<ts>` 在这里防的只是「同一份快照被反复应用」，而那种情形两侧是**同一个字符串**（同一次 DB 读的同一个值），不涉及任何跨链精度问题。`ts` 跨链一致性对**调研 / 澄清**那两个计数才是承重的，而那两个已经按 `repo_id` / `clarification_id` 这类自然键去重，本就不靠 `ts`。
2. **200 条上界对 merge 事件结构性不可达。** 110-03 的截断是「保留**最新** 200 条」，而 `merge` 是最后一个阶段 ⇒ `merge.started` 永远落在被保留的窗口里，被丢掉的只会是早期阶段的事件（这正是截断方向选「保留最新」的原因）。加上融合轮次由校验重试上限封顶（耗尽即 `merge_validation_exhausted`，个位数），距 200 有两个数量级。
3. **加了也删不掉 `Set<ts>` 那条路径。** 改动上线前产生的会话、以及任何 payload 里没有 `attempt` 的事件，仍要走原路径 ⇒ 结果是「新路径 + 旧兜底」两条分支，净复杂度上升而不是下降。
4. **范围纪律。** `architect_merge_adapter.py` 当前不在本 phase 任何 plan 的 `files_modified` 里。为一个上述分析下**不可达**的风险把一个后端 adapter 拉进 wave 1 的作用域，并让 110-05（wave 4，前端）多出一条对 110-01 payload 形状的实质依赖，代价大于收益。

⇒ 若将来 UAT 真的观察到融合轮次数不对，正确处置是**那时**再加 `attempt`（一行 + 一条前端优先取值），而不是现在预防性地扩大 phase 边界。本条与本 plan `<negative_control>` 的「merge 不同 ts 算两轮」用例一并构成该计数的现行保障。

    **4. 阶段指针（🔴 权威顺序）**

    ```
    pointerStage =
        snapshot?.current_stage ∈ STAGE_ORDER  ? snapshot.current_stage
      : 最后一条可识别转移事件的目标 stage      ? 该 stage
    ```

    冲突时以快照为准，且**不打 warn、不报错**（事件截断与时序是正常场景，不是异常）。`current_stage` 是未知 key 时退回事件推出的指针（不崩、不清空）。

    🔴 **序号在完整 7 键上算，可见性过滤放到最后一步做。** 隐藏 `classify` 若在算序号阶段就把它从数组里删掉，后面所有步骤的序号会整体错位一格 —— 症状是「融合已经在跑，界面上还显示在调研」。

    **5. `showClassify`**（F-15）

    `snapshot?.has_classify === true || 见过 'technical_plan.feature.classified'`。

    **6. 单步状态（六态，§A.3）**

    对每个 stage（按完整序号）：
    - 会话 `failed` 且 `failure.stage` 命中该 stage（`failure` 缺失时退回 `current_stage` 命中）⇒ `failed`
    - 会话 `done` ⇒ 全部 `completed`
    - 序号 < pointerIndex ⇒ `completed`
    - 序号 === pointerIndex ⇒ `running`（会话未终态时）
    - 序号 > pointerIndex ⇒ `pending`
    - 🔴 **澄清判 `skipped`**：pointerIndex > clarify 序号 **且** 本会话从未出现任何 `clarification.*` 事件 ⇒ `skipped` + 摘要 `本次无需澄清`。出现过 `clarification.asked` ⇒ 走 `running`（等待中）/ `completed`（已答 / 已超时放行）。
    - 🔴 **中断（§E.3）**：`runtimeActive === false` **且** `snapshot?.status ∈ {'running','waiting_event'}` ⇒ 当前步转 `unknown` + 摘要 `进度未知，可能已中断`，后续步保持 `pending`。
      `status === 'waiting_clarification'` + 不活跃 ⇒ **不算中断**（合法的等待用户），澄清步保持 `running` 但 `pulse: false`。
    - `pulse`：`running` 步仅在 `snapshot?.status ∈ {'running','waiting_clarification','waiting_event'}` **且** `runtimeActive === true` 时为默认（脉冲）；否则 `pulse: false`（它确实不在动）。

    **7. 摘要（§A.4，七套模板 + 澄清子表）**

    全部**纯字面读取**，任一字段缺失 / 类型不符 ⇒ 该摘要为 `undefined`（渲染层整行不渲染），**不产出「暂无」**：

    |---|---|---|
    | 拆分 | `snapshot.segment_count`（F-14：事件流拿不到） | `已拆出 {n} 个需求点` |
    | 路由 | `repo.routing` 的 `candidates.length`（非数组 ⇒ 无摘要） | `命中 {n} 个候选仓` |
    | 召回 | `knowledge.recalling` 的 `hits`（非数字 ⇒ 无摘要） | `召回 {n} 条相关知识` |
