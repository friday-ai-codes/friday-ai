<objective>
构建『对账 + 两模式清理』的服务与 API 地基：`compute_reconciliation(repository_id)` 对比"已索引文件集合 vs 现行排除规则"（复用 Phase 22 `build_matcher_for_repo`，EXCL-06），列出差异；`run_cleanup(repository_id, mode)` 对差异文件逐一调 Phase 23-01 的 `purge_file` 删净派生索引面（EXCL-04），清理后调度 repo_summaries/repo_index_nodes 重建，并埋清理审计事件（D-04）。暴露 REST API：`GET …/reconcile/` 返回差异、`POST …/reconcile/` 接受 `{mode}` 执行清理。`mode=sensitive` 分支委托 23-03 的 `services.sensitive_purge.purge_sensitive_planes`（懒导入，普通模式无依赖）。

Purpose: 这是 EXCL-06 对账与 EXCL-04 普通清理的服务/接口主干——把 23-01 的单文件删除入口升级为"规则驱动的批量对账清理"，并为 23-03 敏感面与 23-04 前端 UI 立好契约。
Output: `server/services/purge_reconcile.py`（新增）、`RepositoryReconcileView` + 路由 + serializer、对账/普通清理守护测试。
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| 已索引数据 → 对账诊断 | 对账漏报会让用户以为已干净，残留明文仍可检索（信息泄漏） |
| client → 清理 API | 未授权调用可破坏他仓索引（完整性 / 越权） |
| 清理执行 → 派生面 | 普通清理不彻底则残留（信息泄漏）；过度清理误删需要数据（完整性） |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-23-05 | Information Disclosure | compute_reconciliation 漏报 | mitigate | 已索引集合取 FileIndex ∪ ChunkRegistry 双源并；匹配器异常不谎报 0 而标 error，避免假"已干净" |
| T-23-06 | Elevation of Privilege | reconcile/cleanup API 越权 | mitigate | permission_classes=[IsAuthenticated]；所有查询/删除带 repository_id；仓库不存在 404（测试守护） |
| T-23-07 | Tampering | 普通清理误删需要数据 | mitigate | 仅对"对账命中排除"的文件清理；purge_file 全程 repository_id 作用域；普通模式不触碰操作记录面 |
| T-23-08 | Denial of Service | 大仓清理阻塞请求线程 | mitigate | 清理经 run_in_background 派发，API 立即 202；摘要重建亦后台 best-effort |
| T-23-09 | Repudiation | 清理无审计痕迹 | mitigate | log_purge_event 埋 purge.started/completed（mode/repo/命中数），供审计里程碑复用 |
</threat_model>
