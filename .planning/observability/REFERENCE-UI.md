# 运维监控大盘 · 参考借鉴与差异适配

**来源：** 某 LLM 转发/网关平台的运维监控页截图（仅参考，**不照抄**）。
**定位差异：** 参考系统是「LLM 转发平台」——一次请求 = 一次代理转发（请求中心）。我们是「Agent 平台」——一次用户动作 = 一次多轮 agent 运行（多次 LLM 子调用 + 工具调用 + 召回 + 容器任务）。所以**布局可借鉴，维度与层级必须按 Agent 重构**。

## 1. 值得借鉴的布局/交互（纳入 M5 UI）

### 1.1 顶部卡片区（直接借鉴结构，换我们的指标口径）

参考用了一排信息卡，结构清晰，建议沿用这套"卡片 + 明细下钻"范式：

| 参考卡片 | 我们对应 | 说明 |
|----------|----------|------|
| 健康分（92 圆环） | **复合健康分** | 由 CPU/内存/错误率/上游错误/队列积压加权算一个 0–100 分 + 健康/警告/严重；一眼看整体 |
| 实时信息（1min/5min/30min/1h tab；当前/峰值/平均 QPS·TPS + sparkline） | **实时速率卡** | 时间窗 tab + 当前/峰值/平均 QPS·TPS + 迷你趋势 |
| 请求（请求数/Token数/平均QPS/平均TPS） | **请求汇总卡** | 入口请求维度 |
| SLA（排除业务保障 0.000% + 异常数） | **SLA 卡**（见 §2 口径） | 关键：SLA **排除业务限制**误差 |
| 请求错误（错误率 + 错误数 + 业务限制数） | **请求错误卡** | 系统错误 vs 业务限制分开计 |
| 请求时长（P99 大字 + P95/P90/P50/Avg/Max） | **请求时长卡** | 分位 |
| TTFT（P99 大字 + P95/P90/P50/Avg/Max） | **TTFT 卡** | 分位 |
| 上游错误（错误率 + 错误数(排除429/529) + 429/529 单列） | **上游错误卡** | 429/529 单独列出 |

### 1.2 资源快照行（借鉴"内联阈值"）

参考把当前快照做成一排，且**把阈值直接写在卡里**（CPU 99.1% 警告60% 严重95%；REDIS 连接259/4096；协程 当前104 警告8000 严重15000；后台任务 总计5）。
→ 我们 SNAP-01~05 沿用：CPU/内存/数据库(连接·活跃·空闲)/Redis(连接 x/maxclients·活跃·空闲)/协程/后台任务，**卡内显示告警阈值**，超阈值变色。

### 1.3 趋势区

- 吞吐趋势：按平台叠加 QPS + TPS(千)。→ 我们按 **provider** 叠加，并可切 `call_source`。
- 错误趋势：参考分 **3 口径**（SLA口径/上游/业务）。→ 我们沿用：系统错误 / 上游错误 / 业务限制 三线。
- 请求时长分布、错误分布（空态友好）。→ 沿用。

### 1.4 告警事件表（列结构几乎可直接用）

参考列：时间 / 级别(P2) / 状态(已恢复) / 平台 / 规则ID(#5) / 标题 + 规则信息 / 持续时间 / 维度 / 邮件已发送。
- 规则信息格式很好：`cpu_usage_percent > 85.00 (current 95.40) over last 5m (overall)` —— **机器可读的规则 + 当前值 + 窗口 + 维度**。建议我们 `AlertEvent.rule_info` 采用同款表达。
- 状态：firing / 已恢复(resolved)；邮件列：已发送 / 已忽略（通知策略）。→ 纳入 ALERT-02。

### 1.5 系统日志面板（与我们 LOG 需求高度一致，借鉴其呈现）

参考顶部计数：**队列 0/5000 · 写入 17145 · 丢弃 0 · 失败 0** —— 正是我们 LOG-02。建议大盘原样展示这 4 个计数。
- 运行时日志配置（实时生效）表单：级别 / 堆栈阈值 / 采样初始 / 采样后续 / 保留天数 + caller/sampling 勾选 + 「保存并生效 / 回滚默认值」。→ 正是 LOG-06，UI 照此排布。
- 过滤器：时间范围 / 开始 / 结束 / 级别 / 组件(如 http.access) / request_id / client_request_id / user_id / account_id / 平台 / 模型 / 关键词。→ 见 §3 维度适配。
- 操作：查询 / 重置 / **按当前筛选清理** / 刷新健康指标。→ 正是 LOG-08。

## 2. 口径细化（参考启发，需补进需求）

参考把"错误"拆成三类，这是它最有价值的一点，我们必须采纳，否则 SLA 失真：

1. **系统错误**：服务自身 5xx/异常 —— 计入 SLA 故障。
2. **业务限制**：非系统故障的"按规则拒绝"。参考里是用户限流/配额；**我们对应 `LLMBusyError`（凭证并发满→"系统繁忙"排队/拒绝）、权限拒绝、输入校验失败** —— **排除在 SLA 故障之外**（否则正常限流会拉低可用率）。
3. **上游错误**：provider 返回的错误，**429/529 单列**，其余上游码另计。

→ 已据此细化 SLA-01/SLA-02/SLA-03（见 MILESTONE-PROPOSAL）。

## 3. 维度适配：他们的「平台/账号/模型」→ 我们的 Agent 维度

参考的核心维度是 `平台(provider) / 账号(API key account) / 模型`。我们要**保留这三个并叠加 Agent 专属维度**：

| 参考维度 | 我们映射 | 备注 |
|----------|----------|------|
| 平台 platform | `provider`（anthropic/openai_*/gemini/ollama） | 保留 |
| 账号 account | `credential`（`ProviderCredential`） | 保留；我们是凭证级并发 |
| 模型 model | `model` | 保留 |
| —（无） | **`call_source`**（22 类：chat/workflow_*/compat/aux_*/container 等） | **Agent 平台核心新增**：区分 AI 调用来源 |
| —（无） | **`source`**（mcp/chat/compat/rest/webhook/workflow/task/scheduler） | 入口来源 |
| —（无） | **关联键**：`conversation_id`/`execution_id`(workflow)/`run_id`(interaction)/`repository_id`/`node`/`tool_name`/`session_id`(container) | Agent 运行可下钻 |
| 用户 user_id | `user_id`（无则 `system`） | 我们更强调归因（CTX 贯穿） |

系统日志过滤器据此调整为：时间/级别/组件/`user_id`/`source`/`call_source`/`provider`/`credential`/`model`/关联键/关键词。（参考的 `client_request_id`≈我们 `request_id`/外部 `X-Request-ID`；`account_id`≈`credential`。）

## 4. Agent 平台必须比参考"多做"的部分

参考是请求中心，**缺**以下我们必须有的（已在方案中）：

1. **召回（RAG）可观测**：召回条数/分层耗时(embedding·sparse·qdrant·rerank)/相关度 score/query+召回内容下钻（MCP + AI 对话两条链）—— 参考完全没有，是我们差异化重点（RAG-01/02）。
2. **Agent 运行层级**：一次入口请求 ≠ 一次 LLM 调用。大盘要能区分「入口请求 QPS（对话/工作流触发/MCP）」与「LLM 子调用 QPS/TPS」与「工具调用」与「容器任务」。靠 `call_source` + 关联键下钻。
3. **并发/排队的 Agent 语义**：参考只有 provider 并发。我们的"排队"含 **索引 / AI 描述生成 / 爬取入库 / 其它异步任务** + provider 并发 + runner 容器并发（RATE-03/SNAP-05）。
4. **调用详情下钻到会话**：AI 对话点进去看该会话**全部请求 + 原始数据**（复用 Interaction Ledger + Conversation/Message）—— 参考只能看单请求日志（LOG-04）。
5. **容器侧 LLM token**：编码/repo描述/深度分析在容器内跑，token 要回流统计（RATE-02 已含）。

## 5. 不照抄 / 不适用的部分

| 参考元素 | 处理 |
|----------|------|
| 「平均账号切换趋势」（API key 轮换/故障切换） | **不直接抄**。我们是凭证级并发限流，无重度账号轮换；如需，弱化为「凭证故障/降级次数」，非首屏 |
| 顶栏「$95791.03 余额」 | 我们没有充值余额概念；可改为**累计/本月 LLM 成本估算**（`ModelUsageRecord.cost_estimate` 已有），可选 |
| 纯请求中心的信息架构 | 重构为 **入口请求 / LLM 子调用 / 工具 / 召回 / 容器** 多层视图 |
| 「排除业务保障」这种网关话术 | 改为我们语境的「排除业务限制（含系统繁忙限流）」 |
