# Quick Task 260726-t2f：feature list 技术方案生成能力（后端链路）

把「给一份 feature list（或 feature list 关联的分支）→ 判定每个功能点是新增还是修改 → 结合仓库调研给出关联仓库 → 强制让用户确认/澄清 → 输出分仓 + 整体技术方案」做成 Friday 的一等能力。

本次只做**后端编排链路**（用户已选 backend_first）。MCP 工具、Skill 文档、对话 agent tool、前端 UI 留待后续 quick 任务。

## 决策（已与用户确认）

| 决策点 | 选择 | 理由 |
|---|---|---|
| 编排落地形态 | 扩展现有 `technical_plan` process，新增 `classify` stage + `feature_list` 入口模式 | 复用已跑通的 ConvergenceSession / 澄清挂起 / 容器调研 / barrier 恢复，不造第二套状态机 |
| 新增 vs 修改判定 | RAG 混合检索 + 能力树路由 + LLM 判定 | 秒级返回、证据可溯源；容器深挖对几十个功能点成本过高 |
| 交付范围 | 后端 process 优先 | 先用单测跑通链路，再接 MCP / Skill / 对话 |

## 关键不变量（实现时必须守住）

- **INV-A 现有链路零扰动**：`classify` stage 在非 `feature_list` 模式下必须 pass-through（不调 LLM、不检索、直接返回 `classified`）。现有飞书 `technical_plan_generation` 模板、对话 `start_plan_research`、MCP `create_feishu_technical_plan` 行为不得改变。
- **INV-B 强制确认**：`feature_list` 模式首轮澄清恒发生，即使路由全部 high 置信。但必须受现有 `_MAX_CLARIFY_ROUNDS` 约束，已答一轮后回落正常策略，杜绝无限挂起。
- **INV-C best-effort**：分类 LLM / 检索失败一律降级（分类不出来标 `unclear`），绝不抛出让 `engine.advance` 落 `failed`。对齐 `decompose_segments.py` 的 fail-soft 范式。
- **INV-D 观测合规**：新 LLM 调用点赋 `call_source`，事件带 `category` / `component` / `duration_ms`，检索结果写 `RetrievalTrace`。
- **INV-E engine 纯度**：stage handler 只返回 `StageOutcome`，绝不自行 `transition`。

## Stage graph 变更

```
现状：decompose → route → recall → clarify → research → merge → __done__
改后：decompose → route → recall → classify → clarify → research → merge → __done__
                                     ↑ 新增
```

只改两处 transitions：`recall.recalled → classify`、新增 `classify.classified → clarify`。merge 的回退目标（`validation_failed_reclarify → clarify`）不变，回退不重跑分类。

**action:**

1. `call_source.py` 新增枚举 `FEATURE_CHANGE_CLASSIFY = "feature_change_classify"`，按现有注释风格标注用途与批次；同步更新类 docstring 的枚举计数与 `.planning/observability/LOGGING-SPEC.md` §4.1 清单。

2. 新建 `feature_classify.py`——**逐段镜像 `decompose_segments.py`**（该文件是本仓 LLM helper 的权威样板）：入口无关纯 helper、不接 IO、`_content_to_text` / `_parse_*_json` / `normalize_*` 三件套、`use_call_source` 标注、异常吞为降级值。

   导出 `aclassify_feature_changes(*, features, evidence_by_key, max_items)`，输入每个功能点及其检索证据，输出归一后的：

   ```python
   {"key": "模块::功能点", "module": str, "name": str,
    "change_type": "new" | "modify" | "unclear",
    "confidence": "high" | "medium" | "low",
    "target_repo_id": str, "reason": str,
    "evidence": [{"file_path": str, "symbol": str, "score": float}],
    "suggested_location": str}
   ```

   `normalize_feature_classifications` 防御 LLM 畸形输出：非法 `change_type` / `confidence` 回退 `unclear` / `low`，缺 `key` 的项跳过，截断到 `max_items`。system prompt 强约束：判 `modify` 必须给出证据中真实存在的 `file_path`，判 `new` 必须给 `suggested_location`，无法判定填 `unclear`（不许猜）。

3. 新建 `classify_adapter.py`——`FeatureChangeClassifyAdapter.classify(session)`：
   - 从 `session.decomposition` 取 `segments`（feature 树展平结果）与 `routing.candidates` 的 repo_id 列表。
   - 逐功能点经 `HybridSearchService(get_provider()).search(query, repository_ids=..., top_k=...)` 取证据（注意：该类是**实例风格**，须显式注入 provider，不读 settings）。检索并发要有上限，避免几十个功能点打爆 provider。
   - 调 `aclassify_feature_changes` 批量判定。
   - 每条命中写 `RetrievalTrace`（kind=CHUNK），best-effort 包 try。
   - 返回 `{"items": [...], "summary": {"new": n, "modify": m, "unclear": k}}`。

4. `protocols.py` 增 `ClassifyProtocol`（与既有 Router/Recall/Clarify Protocol 同风格）。

5. `builtin_processes.py`：
   - 新增 `_h_classify(session, engine)`：**先判模式**——`decomposition.mode != "feature_list"` 时直接 `return StageOutcome(event="classified")`（INV-A，不碰 deps、不产 stage_state）；否则调 `engine.deps.classify.classify(session)` 落 `stage_state.classification`。deps 上没有 `classify` 属性时也走 pass-through（兼容未注入的旧构造）。
   - `_TECHNICAL_PLAN_STAGES` 插入 `classify` StageDef（非 pausable），改 `recall` 的 transitions 指向 `classify`。
   - `_h_decompose` 增分支：`feature_list` 模式下 segments 直接由 `decomposition.feature_segments` 提供（feature 树已是结构化的，不需要 LLM 再拆一遍），仅当其为空才回落现有 LLM 拆分路径。

6. `entrypoint.py`：
   - `start_orchestration` 增 `mode: str = ""` 与 `feature_segments: list[dict] | None = None`，写入 `decomposition`。仅在非空时写键，保持既有会话形态零扰动。
   - `build_orchestration_engine` 的 deps 注入 `classify=FeatureChangeClassifyAdapter()`。

7. `__init__.py` 导出新 adapter。

**verify:** `cd server && uv run pytest tests/services/ -k "process_runtime or decompose or clarify or engine" -q` 全绿；`uv run ruff format --check` + `uv run ruff check` 干净。

**done:** 非 feature_list 会话经过 classify stage 时不产生任何 LLM 调用与 stage_state 变更；feature_list 会话产出带证据的分类结果。

## Task 2：强制仓库确认澄清

**files:**
- `server/services/process_runtime/feature_confirm_questions.py`（新建）
- `server/services/process_runtime/clarify_adapter.py`
- `server/services/process_runtime/entrypoint.py`

**action:**

1. 新建 `feature_confirm_questions.py`——**确定性组装**（不走 LLM，避免"确认仓库"这种关键问题被 LLM 自由发挥漏掉），输入 `routing` + `classification`，输出符合现有卡片契约的问题数组（`question` / `type` / `options` / `recommended`，复用 `normalize_clarification_questions` 做最终归一）：
   - 第 1 题（恒有，multi）：确认关联仓库。options 取 routing 候选 `repository_name`，recommended 取 high/medium 置信项。这是 INV-B 的落点——即使全部 high 置信也照问。
   - 第 2 题（有 modify 项时，multi）：复核判为「修改已有功能」的功能点，让用户勾掉误判的。
   - 第 3 题（有 unclear 项时，multi）：列出无法判定的功能点请用户指认归属。
   - 上限 5 题（对齐现有 `_MAX_QUESTIONS`），功能点过多时按置信度升序取前 N 并在题干注明"其余按分类结果执行"。

2. `clarify_adapter.py`：`__init__` 增可选 `question_builder`（默认 None 走现有 LLM 生成路径）。`clarify()` 内在 builder 存在且产出非空时用其结果调 `create_round`，否则回落现有逻辑。**不改**现有 pending 短路、轮数上界、已答重判这三段逻辑（它们是防死循环的关键）。

3. `entrypoint.py`：`build_orchestration_engine` 增 `force_confirm: bool = False`。为真时注入 `ClarifyAdapter(policy=_always_confirm_first_round, question_builder=build_feature_confirm_questions)`。

   `_always_confirm_first_round(session)`：读 `session.stage_state.classification` 存在即返回 `(True, "请确认关联仓库与功能点分类", [])`。**注意**：该 policy 只在首轮生效——`ClarifyAdapter.clarify()` 已有 `round_count >= _MAX_CLARIFY_ROUNDS` 兜底，且第二轮起 question_builder 应返回空以回落 LLM 重判，避免同一批确认题反复发。这一点在 builder 内按 `round_count` 判断。

**verify:** 新增单测覆盖三条路径——首轮恒发确认题、已答后不重复发同题、`force_confirm=False`（现有入口）行为逐字不变。

**done:** feature_list 会话首轮必定挂起等确认；现有入口的澄清行为无任何变化。
