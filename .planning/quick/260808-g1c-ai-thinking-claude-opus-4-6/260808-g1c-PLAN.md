# Quick Task 260808-g1c

## 背景（实测结论，勿重新调研）

前置排查已完成，以下结论均为实测所得，直接采信：

1. **首字延迟不是自家代码问题。** 端到端实测：SSE 通道 106–132ms 就通了，服务端本地开销仅 ~150ms，其余全在等上游网关。对比 `RequestMetric.ttft_ms`（source=chat_sse）与 `ModelUsageRecord.ttft_ms`（call_source=chat）即可复现该差值。
2. **`claude-opus-4-8`（默认模型）会把思考文本整段抹掉。** 网关原始事件流为 `content_block_start type='thinking'` → 唯一一条 `thinking_delta` 且 `thinking=''` → 只转发约 1128 字节 `signature`。采样 4/4 次全为 0 字符。`claude-sonnet-5`、`claude-opus-4-5`、`claude-fable-5` 同样为 0 字符。
3. **`claude-opus-5` / `claude-opus-4-9` 在该网关不存在**（503 `model_not_found`）。`claude-opus-4-6` 确实稳定下发思考文本（4/4 次、306–464 字符），但**本任务决定不切换模型**，继续用 `claude-opus-4-8`。
4. **后端 `chat_runner.py` 的 `reasoning` 分支逻辑是对的**：`if reasoning:` 收到的确实是空字符串，不是 bug。因此空思考不会产生 thinking part。
5. **前端数据层已经实时累加**（`chat.ts`，默认 `chat-parts-protocol=new`，`part_delta` 原地 append 到 `streamingParts`）。**不需要改 store / SSE 层。**

由此得出本任务的两条主线：

- 有思考文本时（例如用户日后自行换模型、或网关行为变化）→ 全量、实时、默认展开地展示。
- 没有思考文本时（当前默认模型的既定行为）→ 用「正在思考」占位填满那 4–6 秒空档，消除"卡住了"的观感。
