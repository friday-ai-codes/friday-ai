把「派发一次」变成 durable 子任务，DB 为真相源，内存队列删除。所有子改动一次提交（原子）。

**1a. 队列常量**（`durable/queues.py`）：新增 `QUEUE_DISPATCH = "dispatch"`，注释照 `QUEUE_REPO_SUMMARY` 模式写明「durable job 只负责可靠地发起一次派发（标签匹配 + channels send），重活在 Runner 容器内执行；替代 TaskDispatcher 进程内存队列，解决 server 重启丢派发」。同步进 `ALL_QUEUES` 与 `__all__`。

**1b. dispatcher 改造**（`runners/dispatcher.py`）：
- **保留** `DispatchTask`、`_try_assign` 及其全部 helper（`_find_matching_runners`/`_has_active_assignment`/`_increment_tasks`/`_create_assignment`/`_log_dispatch_event`）、`cancel`。`_try_assign` 是 worker 侧的派发执行例程，一字不改其匹配/幂等/监控事件逻辑。
- **删除** `_pending: asyncio.Queue`、`drain_pending`、`on_runner_online`、`on_task_rejected`（内存队列语义整体退役）。
- **`dispatch(task)` 新语义**（两步，⛔ 不再先 `_try_assign` 内联试派——派发动作本身必须先持久化才谈得上可靠）：
  1. **快照持久化**：若 `SubAgentSession.last_output` 尚无 `"dispatch"` 键（编码链已在 `dispatch_coding_task` 落过 → 跳过，逐字保留其行为），则写入 redacted 快照。把「DispatchTask → redacted 快照 dict」抽成 dispatcher 模块级函数 `build_dispatch_snapshot(task)`（剔除 `CREDENTIAL_ENV_KEYS` 键 + 记 `_redacted_env_keys`，键集与 `coding_session_service` 落库处逐字一致），并让 `coding_session_service.dispatch_coding_task` 的落库段改调该函数（⛔ 不留两份剔除逻辑；`CREDENTIAL_ENV_KEYS` 常量迁到 dispatcher 模块并在 chat 侧保留同名 re-export，chat→runners 方向 import 无循环）。
  2. **入队**：`DurableTaskService.defer("durable_runner_dispatch", {"session_id": task.session_id, "attempt": 0}, queue=QUEUE_DISPATCH, lock=f"dispatch-{task.session_id}", initiated_by_user_id=<contextvars best-effort，见 key_findings 7>)`。⛔ 不带 `idempotency_key`（同 session 的合法重派发不能被 todo 去重吃掉；防重的职责在任务体状态守卫），lock 使同 session 派发串行、守卫判据无并发窗口。defer 抛异常时**向上抛**（既有调用方契约：`dispatch_coding_task` 依赖异常触发任务 token 吊销）。
- **共享重建 helper**：把 `consumers._rehydrate_dispatch_credentials` 提为 dispatcher（或 `runners/dispatch_rebuild.py`）模块级共享函数，新增模块级 `arebuild_dispatch_task_from_session(session)`（从 `last_output["dispatch"]` 读快照重建 DispatchTask + rehydrate，形状照 `consumers._rebuild_dispatch_task` 但不绑 runner/assignment——首派时还没有 assignment）。consumers 的两个用点改为委托共享实现，⛔ 不留拷贝。
- **USER_TOKEN 再铸**（首派经队列后内存 metadata 丢失，不补则编码容器首派就挂不上知识工具，是回归）：在两个 mint 点（`coding_session_service.dispatch_coding_task` 与 `blueprint_research_adapter` 的任务 token 铸造处）向 metadata 增加**非敏感**键 `task_token_user_id`（用户 id 字符串，随快照落库，不是凭证）；rehydrate 扩展：`_redacted_env_keys` 含 `env_FRIDAY_TASK_USER_TOKEN` 且 metadata 有 `task_token_user_id` → `mint_task_token(user, session_id, 3600)` 重铸补回（用户查不到/铸造失败 → fail-soft 跳过该键，与既有降级语义一致，记 warning）。consumers 断连重派路径同样受益（原「不重铸」注释相应更新）。

**1c. durable 任务三件套**：
- `durable/tasks_impl.py` 新增 `run_runner_dispatch(*, session_id: str, attempt: int = 0, initiated_by_user_id: str | None = None) -> dict`，形状照 `run_blueprint_resume`（`bind_task_context(source="durable")`、恒不抛、异常文本过 `redact_secrets_in_text`）：
  1. 按 `session_id` 取 `SubAgentSession`，查无 → `{"status": "skipped", "reason": "not_found"}`；
  2. **幂等守卫（用户锁定决策：状态检查而不是禁止重派）**：`session.status ∈ {completed, error, timeout, cancelled}` → skipped(terminal)；`_has_active_assignment(session_id)` 为真 → skipped(active_assignment)（已在跑/已派出，绝不起第二个容器 → 防重复 commit）；
  3. `arebuild_dispatch_task_from_session(session)` 重建（快照缺失 → skipped(no_snapshot) + warning，理论不可达：dispatch() 先持久化后入队）；
  4. `_try_assign(task)`：True → `{"status": "dispatched"}`；False（无匹配 runner / 无空槽）→ **re-defer backoff**：`defer("durable_runner_dispatch", {"session_id", "attempt": attempt+1}, queue=QUEUE_DISPATCH, lock=同值, run_at=now + timedelta(seconds=min(5 * 2**attempt, 300)))`，返回 `{"status": "requeued", "attempt": ...}`。⛔ 不设 attempt 上限——链条由守卫终结（session 终态/被取消后下一跳 no-op），5 分钟封顶的空转成本可忽略；
  5. 观测（本节埋点即 LOGGING-SPEC 自检项）：`runner_dispatch_job_completed`（info，category="caller"，component="runners"，initiated_by_user_id、session_id、task_type、status、attempt、duration_ms）；re-defer 那跳记 `runner_dispatch_requeued`（category="sampling"——周期性 tick 不刷 caller 面）；失败兜底 `runner_dispatch_job_failed`（warning，error 过 redact）。
- `durable/tasks.py` 增 `@app.task(name="durable_runner_dispatch", queue=QUEUE_DISPATCH)` 包壳（keyword-only 形参 `session_id`/`attempt`/`initiated_by_user_id`，中文 docstring 照 `durable_repo_summary` 模式，写明「⛔ 不带 idempotency_key、lock=dispatch-{session_id}」的理由）。
- `durable/handlers.py` 注册 `**payload` 展开 adapter（照 `_blueprint_resume`）。

**1d. consumers 联动**（`runners/consumers.py`）：
- `_handle_task_rejected`：删除 `on_task_rejected` 内存重排；改为标记 assignment rejected 后 `DurableTaskService.defer("durable_runner_dispatch", ...)` 重新入队（同 1b 的 defer 形参；发起用户 `system`），**但必须带退避与上限，防止对着一个持续拒绝的 runner 热循环**：

  - **上限**：`reject_count >= 8`（累计约 20+ 分钟退避窗口）时不再重派，改为把 session 置终态 error（error message 说明「runner 连续拒绝 N 次，派发终止」，过 `redact_secrets_in_text`）并吊销任务 token（复用 `dispatch_coding_task` 失败路径的吊销逻辑，若该 session 有 token），发结构化告警事件 `runner_dispatch_rejected_exhausted`（warning，category="caller"，component="runners"，session_id、reject_count、runner_id）；
  - 未达上限的每次拒绝重派记 `runner_dispatch_rejected_requeued`（category="sampling"，带 reject_count 与 run_at 退避秒数）。
