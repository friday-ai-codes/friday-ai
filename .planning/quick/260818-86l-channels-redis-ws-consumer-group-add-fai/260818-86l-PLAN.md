## 根因（已定位，勿重新调查）

依赖版本（已核对 `server/uv.lock`）：`redis==5.3.1`、`channels-redis==4.3.0`。

1. `redis/asyncio/connection.py:251` `is_connected` 只判 `_reader is not None and _writer is not None`，
   **不看 transport 是否活着** → `connect()` 对死连接直接 return。
2. `ConnectionPool.ensure_connection()`（同文件 1131-1145）只在 `(ConnectionError, OSError)` 时重连；
   死 transport 若 `can_read_destructive()` 干净返回 False，就被原样发给调用方。
3. `send_packed_command`（同文件 483-514）只把 `OSError` 映射成 `ConnectionError`；uvloop 抛的是
   `RuntimeError: unable to perform operation on <TCPTransport closed=True ...>`，落进 `except BaseException` 原样重抛。
4. `redis/retry.py` `Retry._supported_errors` 默认 `(ConnectionError, TimeoutError, socket.timeout)`，
   `RuntimeError` **永不重试**，也不会调用 `fail` 回调（即 `_disconnect_raise` 不执行）。

链路：`RunnerConsumer.connect()` → `channel_layer.group_add()` → channels_redis `ZADD`
（`channels_redis/core.py:493`）→ 池给出死连接 → uvloop 写失败 → `RuntimeError` 直穿 `connect()`
→ uvicorn `send_500_response()` 再抛一次级联异常 → 客户端重连风暴。

## 两个关键实现依据（决定本方案形态，执行时勿推翻）

**依据 A —— 为什么「重试一次」有效（决定 `safe_group_add` 重试 1 次）**
`redis/asyncio/connection.py:508-514` 的 `except BaseException:` 分支里有
`await self.disconnect(nowait=True)` **再** `raise`。也就是说：uvloop 的 `RuntimeError` 抛出前，
该连接已被 `disconnect()`（`_reader/_writer` 置 None）。连接对象随后由
`Redis.execute_command` 的 `finally: await pool.release(conn)` 放回 `_available_connections`，
此时它对 redis-py 而言是「未连接」状态 → 下一次 `get_connection()` → `ensure_connection()` →
`connect()` 会**新建 TCP 连接**。

结论：**第一次失败恰好把死连接清掉**，紧接着的第二次尝试正常落在新连接上。
所以 `safe_group_add` 重试 1 次（合计 2 次尝试、不 sleep）是高性价比的：把一次用户可见的
握手拒绝转成透明恢复。若 Redis 真的挂了，第二次尝试也会失败，最坏代价由每次尝试的
`asyncio.wait_for` 上界（5s）封顶，握手最多多等 ~5s，然后干净拒绝。⛔ 不要改成无限重试。

**依据 B —— 为什么 `socket_timeout` 不能取 5s（决定 settings 的默认值与下限夹取）**
`channels_redis/core.py:104` `brpop_timeout = 5`，`core.py:233` 用
`connection.bzpopmin(channel, timeout=timeout)` 做**阻塞读**。而 redis-py 的
`read_response()`（`redis/asyncio/connection.py:540`）在未显式传 timeout 时用的就是
`self.socket_timeout`，且 `redis/asyncio/client.py:615-620` 的
`_send_command_parse_response` **不会**为阻塞命令放宽超时。

结论：`socket_timeout <= 5` 会让空闲 channel 的 `BZPOPMIN` 每 5s 触发一次假超时
（`redis.TimeoutError` 冒进 `receive()` → WS 收发链路断掉），属于**引入新故障**。
默认取 15s，并在纯函数里把下限夹到 10s（> brpop_timeout 5s + 余量），env 只能往上调、不能往下踩坑。

附注：`retry_on_timeout=True` 会让 redis-py 把 `TimeoutError` 纳入 `retry_on_error`
（`connection.py:178-194`，等价 `Retry(NoBackoff(), 1)`），作用是**超时后断开重连**而不是复用可疑连接；
它是补充，不是主防线——主防线仍是「`socket_timeout` 高于阻塞超时」。

改动 1（settings）只降低概率、**不能**关闭缺口（`health_check_interval` 的 PING 走的也是
`send_packed_command`，死 transport 上同样会抛 `RuntimeError`）。所以改动 2（fail-soft）是必需的
第二道防线，两者是纵深防御，缺一不可。

## 关键行为决策（执行时按此实现，勿自行发挥）

**D1 成功路径不发 `*_started` / `*_completed`。** group 订阅是每条 WS 连接必经的热路径，
成功侧刷 INFO 违反「级别纪律」；连接生命周期事件由各 consumer 既有日志/指标承担。
helper 只在「重试救回」（sampling/info）与「彻底失败」（caller/warning）时发事件，两者都带 `duration_ms`。

**D2 不新增指标口径。** `RequestMetric` 的 `error_class` 是受控四口径、`labels` 走白名单
（`server/common/request_metrics.py:24-48`），为本次失败新增维度会扩大改动面。失败已有结构化事件，
可按 `event` + `component` 在系统日志侧配告警（LOGGING-SPEC §8/§10.9）。评估结论记录于此，
满足 §9「评估是否需要可配置告警阈值」。

**D3 `close(1013)` 在 accept 之前是「拒绝握手」。** ASGI 下未 accept 就 close，服务器（daphne/uvicorn）
以 HTTP 403 回应 upgrade，**1013 不会作为 close frame 送到客户端**；仍然是正确的 fail-soft
（客户端按自身退避重连），关键收益是异常不再逃进 ASGI 服务器。已 accept 的场景
（`MonitorConsumer`）才真正投递 1013。测试按「`close` 被以 `code=1013` 调用且 `accept` 未被调用」断言，
不依赖传输层表现。

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| WS client → consumer | Go runner / 浏览器发起握手；连接可被任意重放/重连 |
| server → Redis (channel layer) | 远端 Redis 不可信「可用」，可随时 reset / 黑洞 |
| exception text → log sink | 上游异常文本可能夹带连接串/凭证片段，落库前必须脱敏 |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-86L-01 | Information Disclosure | `common/channel_groups.py` 日志 | mitigate | `error` 字段一律过 `redact_secrets_in_text`，只记 `error_type`，⛔ 不记 traceback / 不记 host 连接串 |
| T-86L-02 | Denial of Service | WS 握手路径 | mitigate | 单次 group 操作由 `asyncio.wait_for(5s)` 封顶、重试固定 1 次；失败即拒绝握手，⛔ 不无限重试（避免自造重试风暴） |
| T-86L-03 | Elevation of Privilege | `MonitorConsumer` / `NotificationConsumer` / `ChatConsumer` | mitigate | group_add 失败**不得**把连接当成已鉴权/已订阅：`authenticated=True` 与 `groups_joined`/`broadcast_group` 只在订阅成功后写入（D4） |
| T-86L-04 | Tampering | 依赖安装 | accept | 本任务零新增第三方依赖（仅用 stdlib `asyncio`/`time` + 已在用的 `structlog`/`redis`），无需包合法性门禁 |
| T-86L-05 | Availability regression | channel layer 配置 | mitigate | `socket_timeout` 下限夹到 10s（> channels_redis `brpop_timeout` 5s）并有测试守护，避免加固反而打断 WS 收发 |
