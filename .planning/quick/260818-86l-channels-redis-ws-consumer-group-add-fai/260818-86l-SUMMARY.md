# Quick 260818-86l：channels_redis `group_add` fail-soft 加固 Summary

给 channel layer 的 Redis 连接加上健康检查 / keepalive / 有界超时（降低拿到死连接的概率），
并新增 `safe_group_add` / `safe_group_discard` 收口全部 16 处 WS 分组操作——
Redis 抖动时握手被干净拒绝或重试透明恢复，`RuntimeError` 不再逃进 ASGI 服务器引发
`send_500_response` 级联异常。纵深防御两道齐备。

### 与计划的偏离（3 处，均为执行必需，不改设计）

1. **`ws_group_discard_failed` 的测试需要放宽 structlog 过滤级别。**
   计划要求该事件为 `debug` 级（级别纪律），并让测试直接用 `structlog.testing.capture_logs()`。
   实测不成立：`configure_structlog` 用 `make_filtering_bound_logger(INFO)` +
   `cache_logger_on_first_use=True`，而 `capture_logs()` 只原地改写 processor 链、**不动 wrapper
   级别**，且已缓存的 bound logger 不会因重新 `configure` 而降级 ⇒ `logger.debug` 恒为 no-op、
   事件永远捕获不到。
   处理：**保留计划的 debug 级别契约不变**，在测试侧加 `_capture_logs_at_debug()` 上下文管理器
   （临时放宽 wrapper 级别 + 给模块换一个未缓存的 logger proxy，退出时全部还原）。
   这是测试机制修正，不是行为决策改动。

2. **调用点总数是 16 处，不是计划正文写的「13 处」。**

## 残留风险

1. **基础设施抖动本身没修，本次只保证代码存活。** 远端 Redis / Postgres 主机的
   `Connection reset by peer` / `Timeout connecting to server` 是既有事实，不在本任务范围。
   本次改动把「抖动 → `RuntimeError` 逃进 ASGI → `send_500_response` 二次级联 → 客户端重连风暴」
   变成「抖动 → 重试一次透明恢复，或干净拒绝握手 + 一条结构化 warning」。
   **抖动频率不变**，只是后果从「崩」降级为「一次可重试的拒绝」。根治仍需查 Redis 主机/网络。
2. **`health_check_interval` 压不到零。** 空闲 PING 自身走同一条 `send_packed_command`，
   死 transport 上同样抛 `RuntimeError` —— 这正是 fail-soft 必须存在的原因（纵深防御，缺一不可）。
3. **Redis 长时间不可用时 WS 全线不可用。** 两次尝试都失败即拒绝握手（最坏多等 ~2×5s），
   属预期的 fail-soft 行为，不是回归；客户端按自身退避重连。
4. **拒绝握手会被客户端重试。** `close(1013)` 语义上是「稍后重试」，Go runner / 浏览器会重连；
   若 Redis 长期挂着，重连速率取决于**客户端**退避策略（本次未改客户端），服务端侧不再放大。
5. **`socket_timeout` 下限只在纯函数里夹取。** 若将来有人绕过 `_build_channel_layer_host`
   直接手写 hosts dict，下限保护会失效。`test_socket_timeout_clamped_to_floor` 只守函数本身。
6. **新增 5 个 env 变量默认值未在真实抖动环境实测过。** 默认组合（30 / 5 / 15 / true / true）
   按依据 B 推导且已核对生效路径，但「抖动概率实际下降多少」需线上观察
   `ws_group_add_recovered` 与 `ws_group_add_failed` 的比例来验证。
