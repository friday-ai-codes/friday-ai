Coding Agent 要把需求自动跑成 PR，卡点很快就从编码移到了方案。旧的 `technical_plan` 编排只有单轮，一次融合直接出 MergedPlan JSON，给人看的文档和给 AI 编码的执行段都从这一次融合里长出来。选仓只有 high/medium/low 置信度，没有角色语义也没有证据引用；澄清是阶段级问卷，锚不到具体文本；MCP 入口还默认跳过澄清。

2026-07-29 立项重建，产物是技术方案蓝图。一个项目一份结构化文档，六段固定骨架，每条关键结论带可打开的引用，由需求规格门加三大编排阶段产出，再过 AI 对抗审查与人类划线审查。我负责产物 schema、阶段流水线、生命周期状态机、选仓证据融合、审查规则，以及对外的 MCP 工具面与 Skills 分发。

### 项目结果

蓝图作为 v0.20.0 里程碑（Phases 111 至 116）落地，2026-07-29 立项、08-02 收口，35 条需求 34 条完成，之后在真实需求上持续跑批与修复。

截至 2026 年 8 月，统计如下：

- 阶段流水线：intake、decompose、spec_gate、route、repo_research、reroute、repo_confirmation、repo_plan、merge、ai_review 共 10 个阶段，各有独立的暂停语义与产物落库

- MCP 工具面：npm 包 `@friday-ai-codes/mcp` 对外 37 个工具，与服务端契约用快照测试锁死；编码容器内另挂 11 条只读知识工具
- Skills：8 个技能一份来源，IDE 与编码容器同源分发

### 技术挑战与积累

**1. 十阶段流水线与硬确认门**

问题：一次 LLM 融合出全部产物，中间没有可停可查的位置，用户也无处介入。

方案：把一次 LLM 融合拆成 10 个阶段，每个阶段有自己的执行体、产物表和暂停语义。仓库确认门是硬门，调研结束必须把仓库清单、角色建议、职责、适配结论连证据一起交给用户，用户可以删仓、加仓、改判角色、改职责，反馈驱动回调研循环。确认之后仓库集与职责锁定，后面阶段擅自改动会被审查判 BLOCKER。

价值：方案生成从一次问答变成可跨天推进、随时挂起恢复的过程。11 态状态机把用户读到的状态与内部会话状态统一，已确认的版本不可无声改写，要改先驳回再重走人审。

**2. 结构强制与证据强制**

问题：AI 写方案最常见的两种失败是漏段和无据，靠提示词管不住。

方案：把两件事变成 schema 与校验规则。六段骨架、需求规格、验收锚点由 jsonschema 强制，缺段直接校验失败。叙述内容统一为 Block 序列，每个 Block 带引用，引用在文档级池里去重存放。审查阶段查引用覆盖，关键结论无引用判 BLOCKER。审查代理不参与起草，独立跑，结论带 block 级锚点直接生成划线线程。

价值：漏段与无据变成机械可查。Block 同时是划线澄清的锚点、人工编辑的单元和版本 diff 的比较单元。

**3. MCP 工具面：每个节点都能单独调**

问题：编排里的节点只能整条链跑，没法单独验证能力；IDE 和编码容器也要按需取用同一批能力。

方案：把能力收成一层 MCP 工具面。服务端一套工具端点，npm 包对外暴露 37 个工具给 IDE 和命令行，两边契约用 `TOOL_SCHEMA_SNAPSHOT` 快照测试加一致性守卫锁住，schema 改了不同步就红。阶段沙箱把选仓路由、仓库调研这些节点包成可单跑的工具，基于上游产物直接跑。编码容器内另挂 11 条只读知识工具，走短 TTL 任务 token 鉴权，检索类工具只在项目有已完成索引时才暴露。

价值：每个节点可以单独测能力，不用整条链重跑。IDE、对话、容器调的是同一批工具，改一次三处生效。

**4. 给选仓补上意图面知识**

问题：2026-07-29 我用高三提分专项的验收清单在 30 个仓的空间里跑了 5 轮路由，目标 4 仓稳定只命中 2 到 3 个，5 轮结果几乎一字不差。`study-course` 有强相关能力节点却被长 query 稀释掉；`onion-learning` 因为培优课只有一个占位入口被淘汰；`study-plan` 顽固误报，模型按能力树推理「权益鉴权归 study-plan」逻辑自洽，而团队早已把这个职责判给 study-course。

方案：能力树是事实面知识，随索引刷新，回答的是这个仓现在有什么。净新增需求在目标仓没有代码痕迹，服务边界归属又是团队决策，两件事代码里都读不出来。新增 `RepoCharter` 仓库章程补意图面知识，写职责、侧重、落点偏好、边界禁区，一仓一份、版本化、人工确认生效，AI 只能提修订草案。章程与历史落点在 adapter 层与路由分数融合，作为一个分量进 score breakdown。确认门的删仓、加仓动作回灌为章程修订草案。

价值：选仓从纯语义相似度变成可解释、可人工纠正、能积累团队决策的过程。这套判断后来单独长成 v0.23.0 的决策漏斗。

**5. 上下文纪律与会话总线**

问题：多个仓的调研容器同时跑，需要看到彼此的接口契约与依赖声明，还要能等某条上下文出现再继续。方案阶段没有分支，既有项目上下文机制按分支绑定，用不上。

方案：阶段状态只存 id、计数和小摘要，单字段不超过 2KB，子代理拿到的是引用清单，正文自取。跨容器共享走会话级总线，绑定改成任务 token 到会话再到项目，复用编码链已有的 token 铸造，全程不需要分支。等待做两档，分钟级短等待容器保活轮询，跨阶段长等待让容器结构化退出、条目就绪后重新派发，并带互等环检测抛澄清给用户裁决。

价值：并行调研不靠 prompt 传上下文，也不会因为互相等待卡死。会话总线与项目长期记忆分开存放，高频写入不污染人工确认过的记忆。

### AI 驱动的开发效率提升

**1. 把 GSD 的工程机制映射进流水线**

GSD 能长程推进且少幻觉，根因是一组工程机制。我把这些机制做成映射表逐条落进流水线。两段门落成需求规格门，先锁 WHAT，范围外的想法单独存放。歧义量化门落成四维打分，加权超过 0.20 就必须先澄清再进调研。产物落盘加编排只路由，落成阶段产物全部进库、阶段状态只存引用。执行前的方案审查落成有界修订，仓级问题只回对应仓，融合级问题回融合阶段，合计不超过 2 轮就升人审。

价值：防幻觉有了可实现的答案，每条设计决策都能追到一个已被验证过的机制。

**2. Skills 一份来源，IDE 与容器同源分发**

8 个技能（friday、friday-dev、friday-routing、friday-solution、friday-code、friday-feishu、friday-memory、friday-blueprint-stages）作为子模块分发，一条 npx 命令装进 Cursor；其中 4 个在构建期同源拷进任务镜像，容器启动时注入工作区，带 hash 一致性测试挡住第二份手工物料。分支上下文环路写进技能：开工按当前 git 分支召回项目需求与工件，收工回写经验与接口清单，切分支切项目都通用。

价值：IDE 里的人和容器里的 agent 按同一套规矩干活，技能改一次两边同时生效。

**3. 用真实需求当验收标尺**

路由改造的验收锚点取自真实用例，高三提分专项的结果必须包含前端 `onion-learning`、后端 `study-course` 与 `study-user-status`，断言落在机制级而非名次。整条流水线的验收也用同一份 1556 行 feature list 跑真实批次。

价值：设计阶段的每个判断都能被同一份真实语料反驳。前面那三条路由偏差就是 5 轮复跑逼出来的。

**4. 里程碑级的并行开发**

六个相位从立项到收口用了 5 天，主干 640 次提交，同期与另一条里程碑双 worktree 并行。并行的纪律是提前冻结冲突面，路由核心、旧编排六个文件、既有事件契约都不动，前端只新建组件。跑完与另一条线零源码文件交集，合并冲突只剩规划台账和一个 migration 叶子分叉。

价值：AI 把编码速度提上来以后，卡住进度的是两条线互相踩。把冲突面写成纪律再开工，比事后解冲突便宜。

### 项目复盘

**让 Agent 用自由文本回结构化结果**

仓库摘要、仓库适配判定、分仓方案这三个场景原来都靠 agent 在正文里输出 JSON，服务端再解析，配了三个清洗函数兜底。真实跑批里模型会给带围栏的 JSON、半截 JSON，或者压根不给，兜底越写越多。改法是硬切 MCP 工具调用：抽一个共享提交工厂，三个场景各注册自己的 schema，服务端只认工具结果，纯文本和围栏 JSON 明确拒绝；agent 没调提交工具就判失败，不静默兜底；没按协议提交的会话不许续跑。

思考：为什么当时觉得这个比较乐观？

觉得让模型只输出 JSON 是个很小的约束，一句提示词加一个解析函数就够。但正文是自由通道，提示词管不住它。工具调用的参数由 SDK 按 input_schema 校验，约束落在协议层。

如果重新评估，怎么能评估到：

1. 需要机器读的结果就不走自由文本通道。有 schema 校验的工具调用能用就用，省下的是全部清洗与兜底代码。
2. 兜底函数的数量是个信号。同一个入口写到第三个清洗函数，说明通道选错了。

**把证据强制当成一条校验规则**

确认门锁定仓库时会拿当前版本的引用池当白名单过滤证据，而引用池要到融合阶段才建立，锁定那一刻是空的。空集与任何引用求交都是空集，调研阶段产出的选仓证据被全部丢弃，8 条仓库关联理由全部无引用，审查逐条判 BLOCKER，引用覆盖率掉到 0.75，卡在 0.80 的基线下面。代码侧改成先建池再过滤，已落库的那一份另写脚本把证据回填再重跑融合。

思考：为什么当时觉得这个比较乐观？

我把它理解成一条校验规则，审查阶段查覆盖率不够就打回。但证据要跨四个阶段传递，中间每次过滤都可能清空它，清空之后看到的现象是 AI 没给引用，指向的方向是错的。

如果重新评估，怎么能评估到：

1. 跨阶段共享的数据结构要标注什么时候才被填充。任何拿它当白名单的过滤，都要显式处理此刻为空这一种情况。
2. 机械约束需要端到端的真数据回归。单元测试里的引用池永远是造好的非空值，这个 bug 在单测里不会出现。

**按功能点验收长程可恢复**

一次真实跑批里，两个重仓反复调研成功、在最后提交时失败，任务变脏、barrier 死锁，会话以 7/9 个方案失败收场。修完一批之后 8 个方案全部拿到，紧接着 20 次连续的澄清自旋撞上步数上限。查完发现 8 条契约彼此耦合、同时不成立：脏会话被续跑、SDK id 抓取太晚、重试回调不唤醒、barrier 接受裸失败、提交没有上界、两个自环事件共用一个等待状态，还有三处比较只按 UUID 比对，把已锁定的仓当成缺失的仓报出来。

思考：为什么当时觉得这个比较乐观？

我按功能点验收它，断点存了、能续跑、失败能重试，三条单独都成立。可实际要面对的是组合，每个阶段的失败、超时、重复回调、脏上下文交叉在一起，任一条契约不成立，整条流程就退化，而退化以后看到的现象是模型又失败了。

如果重新评估，怎么能评估到：

1. 长程流程的验收项按失败注入列举，不按功能列举。修完这批契约回归跑了 145 个用例才敢说恢复链是通的，这些断言本该提前写出来。
2. 恢复动作要产品化。这次每一步恢复都是手写脚本，两个目录里堆了 17 个、1801 行，每个都要重写一遍守卫；回退、重派、驳回、回填应该是带守卫和审计的一等操作。
