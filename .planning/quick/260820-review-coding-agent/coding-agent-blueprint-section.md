# Coding Agent - 技术方案编写

 P0   Friday AI   Technical Blueprint

「认知」技术方案：AI 时代最后一块需要人守的阵地

Coding Agent 要把需求自动跑成 PR，卡点很快就从编码移到了方案。旧的 `technical_plan` 编排只有单轮，decompose → route → recall → classify → clarify → research → merge 一路下来，最后一次融合直接出 MergedPlan JSON。给人看的 markdown 和给 AI 编码的 execution_plan 都从这一次融合里长出来，质量不稳，人也没有地方插手。

2026-07-29 立项时我先做了一轮现状实证，列出七条差距。选仓只有 high/medium/low 置信度，没有直接仓/间接仓的角色语义，也没有证据引用；产物字段偏执行视角，缺现状分析、实现概述、影响范围、交互流程；融合只有单轮，`MAX_MERGE_RETRIES=1`，没有对抗审查；澄清是阶段级问卷，锚不到具体文本，MCP 链路还默认 `skip_clarification=True`。

这轮重建的产物是技术方案蓝图（Technical Blueprint）。一个项目一份结构化文档，六段固定骨架，每条关键结论带可打开的引用；由需求规格门加三大编排阶段（仓库调研与用户确认 → 分仓方案 → 综合方案融合）产出，再过 AI 对抗审查与人类划线审查。我负责设计并实现产物 schema、阶段流水线、生命周期状态机、章程与路由证据的融合、审查规则。

## 项目结果

蓝图作为 v0.20.0 里程碑（Phases 111 至 116）落地，2026-07-29 立项、08-02 六相位收口，35 条需求 34 条完成，之后在真实需求上持续跑批与修复。

截至 2026 年 8 月，统计如下：

- 阶段流水线：intake、decompose、spec_gate、route、repo_research、reroute、repo_confirmation、repo_plan、merge、ai_review 共 10 个阶段，每个阶段有独立的暂停语义与产物落库
- 产物 schema：`blueprint/v1`，六段骨架 + 需求规格 + must_haves 验收锚点 + 文档级引用池；旧 MergedPlan 作为隐式 v0 只读渲染，零数据迁移
- 代码规模：`blueprint_*.py` 服务端 21888 行；蓝图相关测试函数 1631 个，分布在 104 个测试文件
- 真实跑批：「高三提分专项」1556 行 feature list 跑到 8 个仓的分仓方案与融合蓝图
- 入口与前端：MCP、对话、工作流、飞书导出全入口收编；前端结构化查看器 + 划线澄清 + 知识库技术方案 tab

## 技术挑战与积累

### 1. 从单轮融合重建为可挂起的十阶段流水线

把一次 LLM 融合拆成 10 个阶段，每个阶段有自己的执行体（确定性 service / LLM 单调用 / 容器子代理）、产物表和暂停语义。仓库确认门是硬门，调研结束必须把仓库清单、角色建议、职责描述、fitness 结论、现状摘要连证据一起发给用户，用户可以确认、删仓、手动加仓、改判角色、改职责，反馈驱动回调研循环。确认之后仓库集与职责锁定，后面阶段擅自改动会被审查判 BLOCKER。

价值：方案生成从一次问答变成可跨天推进、随时挂起恢复的过程。11 态生命周期状态机把用户能读到的状态与内部会话状态统一，`confirmed` 之后的版本不可无声改写，要改先驳回再重走人审。

### 2. 结构强制与证据强制

问题：AI 写方案最常见的两种失败是漏段和无据。让模型记得写现状分析，靠提示词不可靠；让它有根据地说，靠提示词更不可靠。

方案：把两件事都变成 schema 与校验规则。六段骨架、requirement_spec、must_haves 由 jsonschema 强制，缺段直接校验失败。所有叙述内容统一为 Block 序列，每个 Block 带 `citations`，Citation 在文档级引用池去重存放，块内只存 id。审查阶段做引用覆盖检查，关键结论无引用判 BLOCKER，事实性断言无引用判 WARNING。审查代理不参与起草，fresh context 独立跑，findings 带 block 级锚点，直接生成划线线程。

价值：漏段与无据从靠提示词祈祷变成机械可查。Block 同时是划线澄清的锚点、人工编辑的 patch 单元和版本 diff 的比较单元，一个基元支撑三种交互。

### 3. 给选仓补上意图面知识

问题：2026-07-29 我用「高三提分专项」的 4000 字符验收清单在 30 个仓的空间里跑了 5 轮完整路由，目标 4 仓稳定只命中 2 到 3 个，5 轮结果几乎一字不差。偏差是系统性的。`study-course` 十轮全漏，能力树里有强相关节点，被长 query 稀释后在全空间 top-50 名额里竞争出局，换一句话摘要当 query 立刻升到第 1；`onion-learning` 被 LLM 阶段淘汰，因为培优课在它的代码里只有一个占位入口；`study-plan` 顽固误报，LLM 按能力树推理「权益鉴权归 study-plan」逻辑自洽，而团队早已把这个职责判给 study-course。

方案：能力树是事实面知识，随索引自动刷新，回答的是这个仓现在有什么。净新增需求在目标仓没有代码痕迹，事实面推不出落点；服务边界归属是团队决策，代码里也读不出来。因此新增 `RepoCharter` 仓库章程作为意图面知识，写职责、侧重、落点偏好、边界禁区，一仓一份、版本化、人工确认生效，AI 只能提修订草案。章程与历史落点召回在 adapter 层与路由分数融合，`charter_match` 作为一个分量进 score breakdown，不改被冻结的 `repo_router_v2.py`。确认门的删仓、加仓动作回灌为章程修订草案。

价值：选仓从纯语义相似度变成可解释、可人工纠正、能积累团队决策的过程。这套判断后来单独长成 v0.23.0 的决策漏斗（画像 → 团队门禁 → 短名单 → 章程/历史 → 放置单元 → 门禁/反思）。

### 4. 上下文纪律与会话级上下文总线

问题：阶段 1 和阶段 2 会同时跑多个仓的调研容器，它们需要看到彼此的接口契约与依赖声明，还要能等某条上下文出现之后再继续。方案阶段还没有分支，既有项目上下文机制按「分支 + 项目」绑定，用不上。

方案：`stage_state` 只存 id、计数和小摘要，单字段不超过 2KB；子代理 prompt 只有任务指令加引用 id 清单，正文由代理侧自取。跨容器共享走新建的 `BlueprintContextEntry` 会话级总线，绑定改成「任务 token → 会话 → 项目」，复用编码链已有的 `mint_task_token`，全程不需要分支。等待做两档，分钟级短等待让容器保活轮询，跨阶段长等待让容器以 `waiting_context` 结构化退出、目标条目就绪后重新派发，并附带互等环检测直接抛澄清给用户裁决。第一道防线仍是按 provider/consumer 关系预排 wave。

价值：多容器并行调研不靠 prompt 传递上下文，也不会因为互相等待卡死。会话级总线与项目长期记忆分开存放，高频调研写入不污染人工确认过的 `ProjectMemory`。

## AI 驱动的开发效率提升

### 1. 把 GSD 的工程机制逐条映射进流水线

GSD 能长程推进且少幻觉，根因是一组工程机制。我把这些机制做成一张映射表，逐条落到蓝图流水线上。SPEC/CONTEXT 两段门在这里是需求规格门，先锁 WHAT，scope 外的想法进 `deferred_ideas`。歧义量化门落成 spec_gate 的四维打分，goal、boundary、constraint、acceptance 加权超过 0.20 就必须先澄清再进调研。GSD 让 subagent 把产物写进磁盘、orchestrator 只读 frontmatter，蓝图这边对应的做法是阶段产物全部落 delivery 表，`stage_state` 只存 id 与小摘要。执行前那道 plan-checker 变成 ai_review 的有界修订，仓级 BLOCKER 只回对应仓的 repo_plan，融合级回 merge，合计不超过 2 轮就升人审。

价值：这张表让防幻觉有了可实现的答案，每条设计决策也都能追到一个已被验证过的机制。

### 2. 用真实需求当验收标尺

路由改造的验收锚点直接取自真实用例，「高三提分专项」的路由结果必须包含前端 `onion-learning`、后端 `study-course` 与 `study-user-status`。断言落在机制级，比较广度加成本身，名次不入断言。整条蓝图流水线的验收也用同一份 1556 行 feature list 跑真实批次，跑出 8 个仓的分仓方案。

价值：设计阶段的每个判断都能被同一份真实语料反驳。前面那三条路由偏差，就是这样被 5 轮复跑逼出来的。

### 3. 里程碑级的 AI 编排开发

六个相位从立项到收口用了 5 天，主干 729 次提交，同期还与另一条 v0.19.0 里程碑双 worktree 并行。并行的纪律是提前冻结冲突面，不动 `repo_router_v2.py`、不动旧 technical_plan 的六个文件、不动 `ConvergenceSessionEvent` 既有契约、前端只新建组件。六相位跑完与另一条线零源码文件交集，合并冲突只剩规划台账、两处同点追加和一个 migration 叶子分叉。

价值：AI 把编码速度提上来以后，真正的约束变成两条线会不会互相踩。把冲突面写成纪律再开工，比事后解冲突便宜得多。

## 项目复盘

### 把「证据强制」当成一条校验规则，忽略了它要跨阶段传递

确认门在锁定仓库时会对 `fitness.citations` 做白名单过滤，白名单取自当时版本的 `content["citations"]`。文档级引用池要到 merge 阶段才建立，锁定那一刻它是空 dict，空集与任何引用求交都是空集，调研阶段产出的选仓证据被 100% 丢弃。下游取「源 rationale.citations ∪ fitness.citations」，两边都空，8 条 `repo_associations[].rationale` 全部无引用，审查规则逐条判 BLOCKER，引用覆盖率被拉到 0.75，卡在 0.80 的基线下面。代码侧改成先建池再过滤，已经落库的那一份还要单独写脚本把证据回填进最新版本，再 rewind 到 merge 重跑。

思考：为什么当时觉得这个比较乐观？

我把「证据强制」理解成一条校验规则，审查阶段查引用覆盖率，覆盖率不够就打回。但证据要跨四个阶段传递，中间每一次过滤都可能把它清空，清空之后审查看到的现象是「AI 没给引用」，看起来像模型的问题。

如果重新评估，怎么能评估到：

1. 跨阶段共享的数据结构要标注「什么时候才被填充」。任何以它为白名单的过滤，都要显式处理「此刻为空」这一种情况，是放行还是报错必须写清楚。
2. 机械约束需要端到端的真数据回归。单元测试里的引用池永远是造好的非空 dict，这个 bug 在任何单测里都不会出现。

### 按功能点验收「长程可恢复」，低估了它依赖多少条契约同时成立

一次真实跑批里，`frontend/onion-learning` 和 `backend/study-course` 反复调研成功、在最后提交 RepoPlan 时失败，任务变脏、barrier 死锁，整个会话以 7/9 个方案失败收场。前一批修复之后 8 个方案全部拿到，紧接着出现 20 次连续的 needs_clarification 自旋，撞上 `advance_step_limit`。查完发现 8 条契约彼此耦合、同时不成立。脏 resume 跨了模式，SDK id 抓取太晚，重试回调不唤醒，barrier 接受裸 failed，结构化提交没有上界，repo_plan 的两个自环事件共用一个 `wait_status`。还有三处比较把 `support_repository_id` 只与关联 UUID 比对，已锁定的 `frontend/onion-learning` 因此被当成缺失的 `onion-learning` 报出来。

思考：为什么当时觉得这个比较乐观？

我按功能点验收它，断点存了、resume 能跑通、失败能重试，这三条单独都成立。可实际要面对的是组合，每个阶段的失败、超时、重复回调、脏上下文交叉在一起，任一条契约不成立整条链就退化，而退化以后看到的现象是「模型又失败了」，指向的方向全是错的。

如果重新评估，怎么能评估到：

1. 长程链路要按失败注入列举验收项，而不按功能列举。每个阶段的失败、超时、重复回调、脏 resume 都要有对应用例。事后补上的 145 个用例本该是前置的。
2. 别名与标识的归一必须收在一处纯函数里。同一个「这个仓是不是那个仓」的判断在 reconcile、review、merge 三处各写一遍，就一定会漂。

### 编排系统的运维动作没有产品化，每次恢复都要手写脚本

跑批出问题以后的每一步恢复都是手写脚本，重跑单仓方案、失效 5 个降级方案、清理过期的澄清线程、回填引用、按新并发重派、抢救孤儿任务。`.planning/quick/260819-feature-list-reingest` 一个目录里就有 16 个脚本、3056 行，每个脚本都要重新实现一遍守卫，检查会话指针有没有漂、检查 8/8 方案还在不在、先跑一遍 dry-run。

思考：为什么当时觉得这个比较乐观？

我把跑批失败当成偶发事件，觉得人工介入一次就过去了。实际上一个 10 阶段、带 HITL 硬门、跨天推进的编排，中途需要人干预是常态。

如果重新评估，怎么能评估到：

1. 编排系统的验收标准里要包含运维动作本身。rewind、redispatch、dismiss、backfill 应该是带守卫和审计的一等操作，而不是 quick 目录下的一次性脚本。
2. 守卫逻辑写一次就够。「拒绝在指针漂移时修复」「一条都没回填上就拒绝继续」这类判断反复出现在每个脚本里，说明它属于服务层。
