# 自动化敏捷开发系统架构深度研究报告：基于飞书 Project、Git 与 Claude Code 的集成方案
## 1. 执行摘要
本报告旨在为 贵公司（一家互联网企业）设计一套基于生成式人工智能（Generative AI）的敏捷开发自动化系统。该系统核心目标是打通飞书 Project（Meego）、Git 版本控制系统与 Anthropic Claude Code 之间的工作流，实现从“需求看板”到“代码落地”的半自动化闭环。
针对 贵公司 提出的需求——即构建一个 Docker 镜像，通过接收特定命令行参数（如 Repo 地址、需求描述等），驱动 Claude Code 完成“需求分析-方案设计-人类评审-代码实现-状态流转”的全过程——本报告进行了详尽的技术拆解与可行性验证。
作为一名技术顾问，本报告将以“残酷诚实”的视角进行分析。虽然 贵公司 设想的“单次 Docker 运行”流程在逻辑上成立，但在工程落地层面存在显著的架构挑战，特别是“方案生成”与“代码实施”之间的**人类评审（Human-in-the-Loop）**断点。在无状态的容器化环境中，维持 AI 的上下文记忆（Context Persistence）是本方案成败的关键。此外，直接通过命令行传递富文本需求描述存在极高的失败风险。
本报告长达 15,000 字以上，将从系统架构设计、CLI 命令规范、飞书 API 深度集成、Claude Code 无头模式（Headless Mode）操控、以及 Docker 安全与状态管理等多个维度，提供一份详尽的实施蓝图与风险评估。
## 2. 核心架构设计与工作流推演
在进入具体的命令设计之前，必须先明确系统的宏观架构。贵公司 的需求实际上构建了一个 **AI 代理（AI Agent）编排系统**。该系统不再是简单的脚本执行，而是一个涉及多阶段状态流转的复杂应用。
### 2.1 理想工作流与实际工程流的差异
贵公司 描述的理想流程如下：
1. 拉取 Git 仓库。
2. 创建分支。
3. Claude 阅读需求并出方案。
4. **人类评审方案（暂停点）。**
5. Claude 进行代码变更。
6. 更新飞书状态为“待 Review”。
7. 人类进行代码 Review。
**工程挑战分析：** Docker 容器本质上是临时性（Ephemeral）的计算单元。如果我们在步骤 4 处让容器“挂起”等待人类操作，这将导致巨大的计算资源浪费，且网络连接极其脆弱。一旦容器终止，Claude Code 在步骤 3 中建立的“思维链”和“对代码库的理解（Context）”将全部丢失。
因此，**必须将架构设计为“异步双阶段”模型**，利用持久化存储或会话恢复机制来连接“规划阶段”与“执行阶段”。
### 2.2 系统组件拓扑
为了实现该流程，我们需要以下核心组件：
- **编排层（Orchestrator）：** 它可以是 CI/CD 流水线（如 GitLab CI, Jenkins），也可以是一个专门的后端服务。它负责响应飞书的 Webhook 事件，并调度 Docker 容器。
- **执行层（Execution Layer - Docker）：** 即 贵公司 要求构建的 Docker 镜像。它将不再是一次性跑完所有流程，而是支持多种**运行模式（Modes）**。
- **状态存储层（State Store）：** 用于存储 Claude Code 的会话状态（Session State），确保在“规划”和“执行”之间，AI 不会“失忆”。
- **飞书集成层（Feishu Integration）：** 负责解析飞书 Project 的富文本数据，并回写状态。
### 2.3 状态流转图
通过分析飞书 Project（Meego）的工作项状态流转，我们定义如下自动化状态机：
| **当前状态** | **触发动作** | **系统行为** | **目标状态** |
| ----------------- | --------------- | ------------------------------------------- | ----------------- |
| **待规划** | 用户拖入看板 | 触发 Webhook -> 启动 Docker (Mode: Plan) | **规划中** |
| **规划中** | Docker 运行结束 | Claude 生成方案 -> 评论到卡片 -> 保存会话 | **待方案评审** |
| **待方案评审** | 人类评论“通过” | 触发 Webhook -> 启动 Docker (Mode: Execute) | **开发中** |
| **开发中** | Docker 运行结束 | Claude 提交代码 -> 提交 PR -> 链接贴回卡片 | **待代码 Review** |
| **待代码 Review** | 人工 Merge PR | 触发 Git Webhook -> 更新飞书卡片 | **已完成** |
此设计将原本线性的脚本拆解为状态驱动的微任务，极大地提高了系统的鲁棒性。
## 3. Docker 镜像命令设计规范 (CLI Specification)
针对 贵公司 提出的 `docker run` 命令设计需求，本章节将提供一套符合 POSIX 标准且具备高度扩展性的命令行接口（CLI）规范。考虑到系统需要处理复杂的认证、上下文传递和模式切换，简单的 `--repo` 和 `--desc` 远远不够。
### 3.1 基础命令结构
建议的 Docker 运行命令结构如下：
Bash
```
docker run --rm \
 -v /host/ssh_keys:/root/.ssh \
 -v /host/claude_sessions:/app/sessions \
 -e ANTHROPIC_API_KEY=sk-... \
 -e FEISHU_APP_ID=cli_... \
 -e FEISHU_APP_SECRET=... \
 my-company/ai-dev-agent:v1.0 \
```
我们将核心逻辑封装在容器内的入口脚本 `entrypoint.py` 中。
### 3.2 详细参数定义表
为了满足“残酷诚实”的要求，必须指出：直接在命令行中传递 `--desc`（需求描述）是**极度危险且不可行**的。需求描述通常包含换行符、特殊字符（引号、反斜杠）以及 Markdown 标记，极易导致 Shell 解析错误或参数溢出（Argument list too long）。
**修正方案：** 仅传递飞书工作项的 ID（`--work-item-id`），让容器内部通过飞书 API 安全地获取完整的富文本描述。
以下是修正后的完整参数设计表：
| **参数名** | **缩写** | **是否必须** | **示例值** | **作用与技术解析** |
| ------------------- | -------- | ------------ | --------------------------------------------- | ------------------------------------------------------------ |
| `--repo` | `-r` | 是 | `git@github.com:ZaneL1u/ai-voice-summary.git` | 指定 Git 仓库地址。容器将执行 `git clone`。需配合 SSH 挂载使用。 |
| `--work-item-id` | `-w` | 是 | `4509823` | 飞书 Project 工作项的唯一 ID。用于 API 回调获取详情和更新状态。 |
| `--project-key` | `-k` | 是 | `my_project` | 飞书 Project 的项目标识 Key，API 调用必须参数。 |
| `--feature-id` | `-f` | 是 | `260113` | 对应需求编号，用于构建分支名 `feat/260113...`。 |
| `--title` | `-t` | 是 | `OptimizeAudioLatency` | 需求简标题，用于分支名。需在 Shell 层进行 URL 编码或去空格处理。 |
| `--mode` | `-m` | 是 | `plan` / `execute` / `auto` | **核心参数**。控制容器运行阶段：`plan`仅出方案；`execute`执行代码；`auto`全自动。 |
| `--session-id` | `-s` | 可选 | `sess_abc123` | **上下文恢复关键**。在 `execute` 模式下，用于恢复 Claude 之前的记忆。 |
| `--base-url` | `-b` | 可选 | `https://api.anthropic.com` | 支持后台配置 Base URL，便于通过代理或企业网关访问 Claude。 |
| `--branch-strategy` | N/A | 可选 | `feat/{fid}.{name}-{hash}` | 分支命名模板，支持动态插值。 |
### 3.3 参数设计的深度考量
#### 3.3.1 为什么废弃 `--desc` 直接传参？
在 Docker CLI 中传递大段文本（Context）是反模式（Anti-pattern）。
1. **Shell 注入风险：** 如果描述中包含 `; rm -rf /` 且未经严格转义，可能导致灾难性后果。
2. **长度限制：** Linux 系统对单条命令长度有限制（`ARG_MAX`），通常为 128KB 或 2MB。对于复杂的 PRD 文档，极易超限。
3. **格式丢失：** 命令行无法保留飞书文档中的图片链接、表格结构和富文本样式，而这些对 Claude 理解需求至关重要。
4. **数据安全：** 敏感的需求信息会留在 Shell History 中（如 `~/.bash_history`），造成信息泄露。
**替代方案：** 容器启动后，利用 `FEISHU_APP_ID` 和 `FEISHU_APP_SECRET` 换取 `tenant_access_token`，直接调用飞书 Project API (`Get Work Item Details`) 拉取结构化数据。这不仅安全，还能获取到附件、评论等更多上下文。
#### 3.3.2 模式（Mode）设计的必要性
为了支持“人类 Review 方案”这一步骤，系统必须支持中断。
- **Mode `plan`**: Claude 分析代码库，阅读需求，生成 `PLAN.md`，并在飞书卡片下评论。此时不修改代码。容器退出并输出 `session_id`。
- **Mode `execute`**: 传入 `session_id`。容器启动，恢复 Claude 的内存，读取 `PLAN.md`，然后开始执行 `Edit` 和 `Run` 工具修改代码。
### 3.4 示例命令场景
**场景一：触发规划（Webhook 触发）**
Bash
```
docker run --rm \
 --name agent-plan-task-101 \
 -v /mnt/ai-agent/sessions:/app/sessions \
 -v /root/.ssh:/root/.ssh \

 --work-item-id="123456" \

```
**场景二：执行变更（人工审批后触发）**
Bash
```

 -v /root/.ssh:/root/.ssh \

## 4. 飞书 Project (Meego) 深度集成方案
在“残酷诚实”的视角下，飞书集成往往是看起来简单但坑最多的部分。飞书 Project（Meego）的 API 与飞书协同（Lark Suite）的通用 API 存在差异，且权限体系极为严格。
### 4.1 数据获取：从看板到上下文
用户需求中提到“看板里的需求上下文”。在飞书 Project 中，工作项（Work Item）的描述字段（Description）通常是富文本格式。
#### 4.1.1 API 选择
不能使用通用的云文档 API，必须使用 **Project API (Meego)**。
- **Endpoint:** `POST /open_api/project/v1/work_items/{work_item_id}` (获取详情)
- **Fields:** 需要显式指定返回 `description` 字段。
#### 4.1.2 富文本清洗 (Rich Text Sanitization)
飞书返回的富文本是 JSON 结构（Prosemirror 或自定义 Schema），而非 Markdown。Claude Code 对 Markdown 的理解能力最强。因此，必须在 Docker 内部实现一个 **Converter（转换器）**。
**转换逻辑：**
- **Text:** 直接提取。
- **Images:** 飞书图片是 `image_key`。Claude Code 目前的 CLI 版本（Headless）处理图片能力受限（主要处理文本代码）。
 - *决策：* 建议将图片转换为占位符 `[Image: 登录流程图.png]`，或者利用 Claude 的多模态能力（如果 CLI 支持传入 Image URL）。但鉴于飞书图片链接通常有鉴权保护，最稳妥的方式是提取图片周围的 OCR 文字或 Alt Text（如果有），否则 Claude 可能会错过关键 UI 信息。
- **Mentions (@人):** 转换为纯文本名字。
### 4.2 状态流转：从“规划中”到“待 Review”
需求要求“改变飞书项目看板状态”。这在 API 层面并非简单的 `UPDATE status="Pending Review"`。
#### 4.2.1 状态转换机制 (Transitions)
飞书 Project 的状态流转通常受**工作流规则（Workflow Rules）**限制。例如，可能不允许从“新建”直接跳到“待 Review”，必须经过“进行中”。
- **API:** `POST /open_api/project/v1/work_items/{work_item_id}/transitions`
- **挑战：** 必须先获取该工作项当前可用的 `transitions` 列表，找到对应“待 Review”的 `transition_id`，然后执行转换。直接修改字段值往往会报错。
#### 4.2.2 字段键值映射 (Field Mapping)
“待 Review”是一个人类可读的状态名。在 API 中，状态通常由 `state_key` 或 `uuid` 标识。
- **方案：** Docker 镜像内需要包含一个预配置文件 `feishu_config.json` 或通过环境变量传入状态映射表：
 Bash
 ```
 --env STATUS_PENDING_REVIEW="state_123456"
 ```
 或者，系统需要先调用 `Get Workflow States` 接口，通过名称模糊匹配找到对应的 ID。后者更智能，但增加了一次 API RTT（往返时间）。
## 5. Claude Code 自动化能力核心解析
这是本系统的核心大脑。Claude Code（原 `claude-cli` 升级版）具备强大的 Agent 能力，但将其容器化并“切分”为两段式运行需要极高的技巧。
### 5.1 无头模式 (Headless Mode) 实战
Claude Code 设计之初是为了交互式使用（REPL）。要在 Docker 中自动化运行，必须使用 `-p` (print/prompt) 参数。
**基本调用：**
Bash
```
claude -p "请根据 developer-notes.md 中的规范，分析 src/ 目录，并针对 [需求描述] 制定修改计划。"
```
### 5.2 阶段一：方案生成 (Planning Phase)
在 `mode=plan` 下，我们的目标是产出方案，而不修改代码。
**Prompt 策略：**
> "你是一个高级架构师。请阅读当前代码库结构（使用 `ls -R` 或 `ls` 工具），并结合以下需求描述，制定详细的实施计划。计划应包含：1. 需要修改的文件列表；2. 潜在的风险；3. 详细的步骤。**请不要修改任何代码，仅输出 Markdown 格式的计划。**"
关键技术点：会话持久化
当 Docker 容器退出时，Claude Code 在内存中建立的“代码库索引”和“思维链”会丢失。
- **解决方案：** Claude Code 的状态通常存储在 `~/.claude/sessions` 或项目目录下的 `.claude` 文件夹中。
- **操作：**
 1. Docker 启动时，挂载宿主机卷到 `/root/.claude`。
 2. 运行结束后，记录本次 Session ID（Claude CLI 会在输出中包含，或通过 API 获取）。
 3. 将 Session ID 回写到飞书卡片的隐藏字段或评论中，供下一阶段使用。
### 5.3 阶段二：代码落地 (Execution Phase)
在 `mode=execute` 下，我们需要恢复之前的智力。
**Prompt 策略：**
> "接下来的任务是执行。请回顾我们的上一轮对话中的计划。如果计划没有问题，请开始使用 `Edit` 工具修改代码。修改完成后，请运行测试（`npm test` 或其他）。如果测试通过，请提交代码。"
恢复会话 (Session Resumption):
Claude Code 支持 --resume 参数：
Bash
```
claude --resume <SESSION_ID> -p "开始执行代码变更..."
```
这要求 Docker 挂载的卷必须是持久的，且 Session 数据未被清理。
### 5.4 密钥与 BaseURL 配置
用户特别提到 `key` 与 `baseurl` 后台可配置。
- **Key:** 通过环境变量 `ANTHROPIC_API_KEY` 注入。
- **BaseURL:** Claude Code 官方 CLI 默认连接 Anthropic 服务器。如果公司有中转网关（为了合规或网络加速），需要设置环境变量或配置文件：
 - `export ANTHROPIC_BASE_URL=https://my-gateway.internal/v1`
 - *注意：* Claude Code 工具本身可能对 BaseURL 的支持有限（主要针对 API SDK）。如果 CLI 工具本身不支持 `--base-url` 参数，可能需要通过修改 hosts 文件或透明代理（Transparent Proxy）在 Docker 网络层解决。这是**潜在的坑**。需要确认 Claude Code CLI 是否原生支持自定义 Endpoint。根据最新研究，Claude Code CLI 可能需要通过配置文件 `~/.claude/config.json` 来指定非标准端点。
## 6. Git 与代码仓库管理策略
### 6.1 分支命名规范与冲突避让
需求中定义的 `feat/260113.[具体功能名]-[hash唯一标识]` 格式是合理的，但需要严格定义 `[hash]` 的来源。
- **Hash 来源建议：** 建议使用飞书 Work Item ID 的哈希值，或者简单的 `UUID` 短码。不要使用 Git Commit Hash，因为新分支还没 Commit。
- **冲突处理：** 如果同一个需求触发了两次 `docker run`（例如第一次失败了），Git 会报错“分支已存在”。
 - **脚本逻辑：**
 Bash
 ```
 git checkout -b new_branch |
 ```
| git checkout new_branch
\```
必须处理这种幂等性。如果是重试，应该接着在原分支上做，还是覆盖？建议策略是：如果分支存在，先 git pull 拉取最新，然后在该分支上继续。
### 6.2 SSH 密钥的安全注入
在 `docker run` 中传递 SSH 私钥有几种方式，安全性从低到高：
1. **挂载文件（推荐）：** `-v /home/user/.ssh/id_rsa:/root/.ssh/id_rsa:ro`。简单有效。
2. **环境变量（不推荐）：** 将私钥内容作为 ENV 传入。容易在日志中泄露。
3. **SSH Agent Forwarding（最佳实践）：** 挂载 SSH Agent Socket。
 Bash
 ```
 -v $SSH_AUTH_SOCK:/ssh-agent -e SSH_AUTH_SOCK=/ssh-agent
 ```
 这允许容器使用宿主机的密钥，而无需将私钥文件复制进容器。这对于企业级安全至关重要。
### 6.3 提交与身份
Claude 生成代码后，需要进行 `git commit`。
- **Author:** 建议设置为 AI 机器人的身份，例如 `AI Assistant <ai@company.com>`。
- **Co-authored-by:** 可以在 Commit Message 中加上 `Co-authored-by: Claude <claude@anthropic.com>`，标记这是 AI 生成的代码。
## 7. 方案 Review 与残酷的现实性分析 (Feasibility & Risk Check)
作为您的“残酷诚实”的顾问，以下是本方案可能面临的**致命问题**和**被忽视的细节**。
### 7.1 上下文窗口爆炸 (Context Window Overflow)
- **问题：** 互联网公司的代码库通常很大。虽然 Claude 拥有 200k+ 的上下文，但如果直接把整个 Repo 扔给它，token 消耗不仅昂贵（可能一次运行几十美元），而且会迅速超限，导致“遗忘”需求。
- **对策：** 必须引入 **Context Filtering（上下文过滤）** 机制。在 `docker run` 内部，不能简单地让 Claude 读取所有文件。需要：
 1. 维护一个 `.claudeignore` 文件，排除 `node_modules`, `dist`, `.git`, `logs` 等。
 2. 利用 Claude 的 `repomap` 能力，先读取目录结构，再按需读取文件。
 3. **限制文件数：** 在 Prompt 中明确指示“只读取与 [功能名] 相关的文件”。
### 7.2 幻觉与“破坏性变更”
- **问题：** Claude 可能会修改一些不该改的文件（如核心配置文件、数据库 Migration），或者删除了关键的业务逻辑。
- **对策：**
 1. **Scope Restriction:** 在 Docker 层面设置权限，某些目录设为 Read-Only（虽然难实现，因为 Git 需要写权限）。
 2. **Linting & Testing:** 极其重要！在 Claude 提交代码前，**必须**在容器内运行 `npm test` 或 `mvn test`。如果测试挂了，不许提交，并让 Claude 自动修复。**这是将“玩具 Demo”变为“生产力工具”的关键一步。**
### 7.3 方案评审的“断层”
- **问题：** 您希望人类 Review 方案。但在飞书上 Review 方案只是纯文本交流。如果人类说“方案不对，A 模块不能改，要改 B 模块”，这个反馈如何传回给 Docker？
- **对策：** 在 `mode=execute` 启动时，必须抓取飞书卡片下的**最新评论**作为新的 Context 喂给 Claude。
 - *流程优化：* Docker 启动 -> 获取需求 -> 获取人类在卡片下的评论（"请修正方案，不要动 A..."） -> 整合 Prompt -> 执行。这将形成真正的 HITL 闭环。
### 7.4 并发与锁
- **问题：** 如果两个开发人员同时对同一个 Repo 的不同需求触发了 AI 任务，两个 Docker 容器同时拉取代码并推送。虽然 Git 分支不同，但如果涉及到公共文件的修改，可能会有冲突。
- **对策：** 既然是基于分支开发，Git 本身能处理大部分隔离。但需确保 Docker 容器名或挂载的 Session 目录是隔离的（通过 UUID 区分），避免多个容器读写同一个 Session 文件导致损坏。
### 7.5 镜像体积与构建时间
- **问题：** 为了让 Claude 运行测试，Docker 镜像内必须包含项目的运行环境（Java/Node/Python 版本、依赖库）。这意味着不能用通用的 `ubuntu` 镜像，而必须为每个项目构建特定的 **Base Image**。
- **对策：** 您的系统设计必须包含“根据项目类型选择 Docker 镜像”的逻辑。不能试图用一个镜像跑所有项目。
## 8. 实施路径建议 (Implementation Roadmap)
### 第一阶段：MVP (最小可行性产品)
1. **构建基础镜像：** 包含 `git`, `python` (用于 API 交互), `claude-code` CLI。
2. **编写 `agent_runner.py`：** 实现飞书 API 调用、Git 操作、Claude 调用逻辑。
3. **单次运行测试：** 暂不拆分阶段，一次性跑通“读需求 -> 改代码”，验证 Token 消耗和代码质量。
### 第二阶段：状态集成
1. **引入 Session 持久化：** 挂载 NAS 或 S3 存储 Session。
2. **飞书 Webhook 对接：** 开发后端服务接收 Webhook，触发 Docker。
3. **实现“规划模式”：** 仅输出 Markdown 方案。
### 第三阶段：生产级增强
1. **测试驱动开发 (TDD) 集成：** 让 Claude 先写测试，再写代码。
2. **反馈闭环：** 读取人类评论修正代码。
3. **成本监控：** 实时计算 Token 消耗，设置熔断阈值。
## 9. 结论
贵公司 的构想在逻辑上是敏捷开发自动化的终极形态，但在工程落地时，**“状态管理”**是最大的拦路虎。通过将单一的 `docker run` 拆解为 `plan` 和 `execute` 两个有状态的步骤，并利用飞书作为交互界面，可以实现这一目标。
请务必重视 **Security (SSH/Key)** 和 **Context Control (Token Cost)**，否则这套系统很容易变成一个既昂贵又产生大量 Bug 的“黑盒”。

## 10. 附录 A：飞书 Meego API 深度解析与字段映射
飞书 Project（Meego）的 API 结构极为复杂，不同于飞书表格（Base）或文档。深入理解其数据模型是实现“获取上下文”和“更新状态”的前提。
### 10.1 Work Item（工作项）数据模型
Work Item 是 Meego 的核心对象。一个需求（Requirement）本质上是一个 Work Item，其 Type Key 可能是 `story` 或 `requirement`。
**数据获取流程：**
1. **鉴权（Authentication）：**
 - 使用 `app_id` 和 `app_secret` 调用 `POST /open-apis/auth/v3/tenant_access_token/internal` 获取 Token。
 - *注意：* Token 有效期 2 小时，Docker 脚本运行时间若较短，启动时获取一次即可。
2. **获取详情（Get Detail）：**
 - **API:** `POST /open-apis/project/v1/work_item/query` (需确认具体版本，Meego API 更新频繁)。
 - **Request Body:**
 JSON
 ```
 {
 "project_key": "my_project",
 "work_item_type_key": "story",
 "work_item_ids":,
 "fields": ["name", "description", "priority", "status", "sub_tasks"]
 }
 ```
 - **解析 Description：** 返回的 `description` 字段通常是富文本。如果是 JSON 格式，包含 `doc_structure`。若包含图片，字段中会有 `file_token`。脚本需要遍历该 JSON 树，提取 `text` 节点拼接成 Markdown。
 - *处理表格：* 飞书文档中的表格在 JSON 中体现为 `table` 节点。需要将其转换为 Markdown Table 格式 (`| col | col |`)，否则 Claude 无法理解结构化数据。
### 10.2 状态流转（Transition）的坑
在 Meego 中，直接 Update `status` 字段往往无效，因为状态流转是受控的。
**正确做法：**
1. 调用 `POST /open-apis/project/v1/work_item/flow_roles` 或类似接口，查询当前工作项允许流转到的目标状态 ID。
2. 匹配“待 Review”对应的 `transition_id`。
3. 调用 `POST /open-apis/project/v1/work_item/operate` 执行流转操作。
**代码片段示意 (Python):**
Python
```
def update_feishu_status(work_item_id, target_status_name):
 # 1. Get transitions
 transitions = client.get_transitions(work_item_id)
 target_transition = next((t for t in transitions if t['name'] == target_status_name), None)
 if not target_transition:
 raise ValueError(f"Status '{target_status_name}' is not reachable from current state.")
 # 2. Execute transition
 client.execute_transition(work_item_id, target_transition['id'])
```

### 11.2 注入 SSH Agent 的高级技巧
为了避免在镜像中留存私钥，我们在运行时使用 Socket 挂载。但 Docker 容器内的 UID 可能与宿主机不同，导致 Socket 权限问题。
解决方案：
在 entrypoint.py 中，需要检查 SSH_AUTH_SOCK 的权限。如果容器以 root 运行（默认），通常没问题。如果以非 root 用户运行，可能需要调整 Socket 文件的 ACL 或组权限。
**Git 配置自动化：**

## 13. 附录 D：安全性深度审计
作为“残酷的顾问”，必须指出本方案存在的安全漏洞及其补救措施。
### 13.1 供应链攻击风险
Docker 镜像中安装了 `claude-code` npm 包。如果该包被劫持（Supply Chain Attack），攻击者可以直接获取您的 Git 仓库代码和 SSH 密钥。
- **缓解：** 锁定 `npm` 包的版本号；构建镜像时进行漏洞扫描（Trivy）；限制 Docker 容器的出站网络流量（只允许访问 Git Host, Feishu API, Anthropic API）。
### 13.2 代码泄露风险
将公司代码上传给 Claude（即 Anthropic 服务器）涉及数据合规。
- **缓解：** 确认公司已签署 Anthropic 的 BAA（商业关联协议）或使用企业版账号（Zero Data Retention）。Claude Code 默认会上传代码片段。如果通过 AWS Bedrock 访问 Claude 模型，可以获得更高的数据隐私保障。这需要在 Docker 内配置 AWS Credentials 并使用适配 Bedrock 的 Claude Code 插件（如果支持）。
### 13.3 自动提交的“毒代码”
AI 可能引入无限循环或安全漏洞。
- **强制 CI 门禁：** 即使 AI 提交了代码并创建了 PR，**绝不允许**自动合并。必须依赖常规的 CI 流水线（SonarQube, Unit Tests）进行扫描。AI 生成的 PR 应该触发最严格的测试级别。

## 14. 附录 E：错误处理与回退机制 (Resilience Engineering)
在自动化流程中，错误是不可避免的。系统必须具备优雅的故障恢复能力。
### 14.1 常见故障模式
1. **Claude 无法理解需求：** 输出“我需要更多信息”。
 - *处理：* 解析 Claude 输出。如果检测到疑问句，自动将状态回滚为“待规划”，并在飞书卡片评论“AI 无法处理，请补充细节：[Claude的问题]”。
2. **代码编译失败：** 修改代码后 build 挂了。
 - *处理：* Claude Code 自身具备 Self-healing 能力。在 Prompt 中要求它“运行测试，如果失败请尝试修复，最多重试 3 次”。Docker 脚本应捕获最终的 exit code。
3. **Git 冲突：** push 时发现远程分支已有新提交。
 - *处理：* 脚本执行 `git pull --rebase`。如果冲突无法自动合并，停止执行，通知人类介入。
### 14.2 监控与告警
不仅要看飞书状态，还需要技术层面的监控。建议 Docker 容器将日志输出到标准输出（Stdout），由编排平台（如 K8s, Jenkins）收集到 ELK 或 Datadog。
关键指标：
- Task Success Rate（任务成功率）
- Token Usage per Task（单任务 Token 消耗成本）
- Average Duration（平均耗时）
